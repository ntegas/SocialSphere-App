## 2. Запрещено ВСЕГДА (жёсткие правила)

- `!!` (force-unwrap) и `database!!` — только безопасный доступ (`?:`, `val x = nullable`)
- `resolveActivity()` (Android 11+ возвращает null) — `startActivity` в try-catch
- хардкод UI-строк при наличии ресурса — только `stringResource`, сразу в **3** strings.xml
- `enum.name` в UI — только `.label(context)`
- `mutableStateOf` для настроек — только `PersistedMutableState` (диск)
- `LocalDate.now().toString()` для datetime-полей — нужен ISO_LOCAL_DATE_TIME
- пустые `onClick = {}` / `onCheckedChange = {}` — обманка хуже отсутствия контрола
- `kotlinOptions { }` — только `kotlin { compilerOptions { } }`
- свитч/контрол без реального поля в модели — обманка, удалять
- переписывать файл целиком по «улучши/почини» — только точечные правки

## 3. Рабочий цикл и дисциплина (нарушение = повтор старых ошибок)

1. **Один шаг = одна вещь.** Никаких «заодно».
2. **Сначала читай реальный код** (свежий grep/Read), потом пиши. Якоря — только из
   свежего вывода, НЕ из памяти. Проверяй сигнатуры, имена enum-значений, состав object,
   что private/public **перед** использованием.
3. **Если правка не нашла якорь — СТОП, перечитай.** Не угадывать повторно.
4. **Реестр ограничений:** перед UI-правкой выписать «делать/не делать» из последних
   сообщений пользователя, сверить (пример: «убрать стрелки» = не возвращать шевроны).
5. **Сохранность функций:** не переписывать блок, не перечислив все его функции и не
   подтвердив, что каждая сохранена.
6. **Анти-хардкод:** после UI-правки grep участка на строковые литералы без `R.string`.
7. **`qa_check.py` ЗЕЛЁНЫЙ перед каждой выдачей.** (см. §9 — как запускать в этой среде)
8. **Первая `e:`-строка компилятора важнее десяти статических догадок.** Цикл:
   сборка → первая ошибка → фикс → сборка. `finished` + warning ≠ провал; паниковать
   только на `failed` + `e:`.

## 6. Архитектурные инварианты (наработаны и проверены)

- **Интенты** — только `ExternalActionHandler.startIntentSafely` (локализованный
  контекст ≠ Activity; прямой startActivity молча падает).
- **Дни рождения / FREQ=YEARLY** — в отображении только через `effectiveDate()`
  (utils/CalendarUtils.kt); сырые даты прошлого невидимы навсегда. В детали повтор
  показывать через `RecurrenceMode.fromRule()` (не сырой RRULE «FREQ=YEARLY»).
- **lastContactDate** — date-only `.take(10)` при записи И чтении.
- **Размеры** — только `AppStateStore.setSizeInfo()` (синхронизирует 3 места);
  `updateNote` НЕ трогает lastContactDate.
- **Тяжёлые filter/sorted/groupBy** — в `remember { derivedStateOf }`; пер-строчные — `remember(id)`.
- **Тяжёлые экраны с мультивыбором** (фильтры) — локальное состояние в листе/шторке,
  пуш к родителю по «Применить»/закрытию, иначе пересчёт списка на каждый тап тормозит.
- **Скролл-контейнер под шапкой/табами в Column** — `Modifier.weight(1f)`, НЕ `fillMaxSize()`
  (иначе прокрутка схлопывается до полэкрана — баг ловился 3+ раза).
- **Настройки** — каждый контрол пишет в `AppSettings` (PersistedMutableState) и реально меняет.
- **Manifest** — `configChanges` на MainActivity не удалять (поворот стирал формы);
  `android:enableOnBackInvokedCallback="true"` на `<application>`.
- **GoogleMap** — только после проверки Google Play Services; `cameraState.animate()`
  в try-catch; `isMyLocationEnabled` только при выданном разрешении.
- **BroadcastReceiver с async-работой** (BootReceiver) — `goAsync()` + `pendingResult.finish()`,
  иначе процесс убьют до конца корутины (напоминания не восстановятся после reboot).
- **Новый контакт** — телефоны/email/мессенджеры/связи писать с `editedContactId`,
  НЕ с `"new"` и НЕ с новым случайным UUID (иначе данные/связи теряются).
- **addContact** — синхронизировать ГЛОБАЛЬНЫЕ `addresses`/`companyRelations` сразу
  (как `updateContact`), иначе связь контакт↔компания и адреса на карте не видны до перезапуска.

## 7. База данных и сохранность (критично)

- Текущая БД **version = 7**, миграции 1→7 прописаны, `exportSchema=true` (схемы в `app/schemas/`).
- При добавлении/изменении @Entity — **обязательно** version++ И миграция (даже no-op,
  если SQL не менялся, но identity-hash разошёлся).
- Удаление приложения стирает БД → обновляться **установкой поверх**.
- Перед обновлением/слиянием дублей — «Сохранить JSON» (полный бэкап). Восстановление —
  upsert по id (ничего не удаляет, сохраняет createdAt). Импорт бэкапа проверяет `version ∈ 1..5`.
- Краш `Room cannot verify data integrity (identity hash)` = схема изменилась без version++.
- destructive fallback — ТОЛЬКО в debug; в release падать явно, не стирать данные.

## 8. Дизайн-система и принципы (уровень Apple — для всего)

- **Цвета по смыслу:** `primary #4F3DC7` — действия/акценты; `tertiary` — даты/события;
  `error` — просрочка/опасное; `secondary` — второстепенный текст.
- **Карта/легенда:** дом = синий, работа = зелёный, компания = фиолетовый, выбранный = оранжевый —
  цвета маркеров, легенды и списка ДОЛЖНЫ совпадать.
- **Формы SocialShape:** поля/чипы 8, карточки 16, bottom sheet 24, аватары/бейджи 50%.
  Отступы кратны 4dp.
- **Apple-форма (сложные экраны):** сгруппированный inset-list компактных строк
  (слева подпись, справа значение серым + шеврон). Тип/выбор = ОДНА строка → пикер,
  НЕ сетка чипов на пол-экрана. Не прятать нужное под «Подробнее» с гигантским скроллом.
- **Дата/время:** только пикерами (барабан-wheel + пресеты «Сегодня/Завтра»), не ручным вводом.
- **Обнаруживаемость:** пустое состояние = точка входа («+ Добавить …», не «Нет данных»);
  действие — в заголовке блока; один акцент на экран; подпись у неочевидных иконок;
  редактирование — тапом по блоку, не мелким карандашом.
- **Эргономика:** тап-цели ≥48dp; частое — в зоне большого пальца; живую карту не класть
  в общий скролл (фикс. высота).

## 9. Среда сборки и команды (ВАЖНО — особенности этой машины)

- **Java не в PATH.** Использовать JBR из Android Studio:
  `export JAVA_HOME="/c/Program Files/Android/Android Studio/jbr"` (Git Bash) перед `./gradlew`.
- **Сборка:** `cd ss-v1 && ./gradlew assembleDebug --no-daemon`.
- **qa_check:** запускать ИЗ КОРНЯ `C:\ss` с UTF-8, иначе падает на Windows cp1253:
  `cd /c/ss && PYTHONIOENCODING=utf-8 python qa_check.py`.
- **⚠️ Эта среда НЕ качает новые зависимости из Maven** (офлайн; работают только закэшированные).
  Любая новая `implementation(...)` → «Could not find» и красная сборка. Новые библиотеки
  (Tesseract, ML Kit, CameraX) добавляются только на машине владельца с сетью.
- **Бинарные ассеты** (языковые модели OCR ~10 МБ и т.п.) ассистент дать не может —
  их скачивает владелец и кладёт в `assets/`.
- Распаковка — короткий ASCII-путь (`C:\ss\`); `android.overridePathCheck=true` уже стоит.
- CI (GitHub Actions): только `checkout@v4`/`setup-java@v4`/`upload-artifact@v4`; SDK+Gradle через
  wget; везде `working-directory: ss-v1`. Запрещено: firebase без json, roborazzi, кастомный
  signingConfig, `actions@v3`, `android-actions/setup-android`.
- Git: репозиторий инициализирован 2026-06-22 (раньше был не-репо).

## 10. Продуктовые решения (смысловые)

- **ImportanceLevel:** обычный → важный → ключевой (топ-приоритетные люди).
- **FORD «Семья» vs «Связанные люди»:** «Семья» = семейные роли; «Связанные люди» в Обзоре =
  только НЕсемейные. Роли с обеих сторон (firstRole=моя, secondRole=его). Добавление связей —
  в Обзоре в режиме редактирования И в форме контакта (секция «Семья и отношения»).
- **Событие на нескольких людей** — `links` список; UI = мультивыбор.
- **Подарки** — один источник правды = вкладка «Подарки» (`GiftIdea`, IDEA→BOUGHT→GIVEN).
- **«Где познакомились»** — в «Обзоре». **Адреса:** рабочие → «Работа», дом/прочее → «Связь»
  (и на карте: личные на вкладке «Контакты», рабочие — на «Работа»).
- **Телефоны** дедуплицируются по последним 10 цифрам.
- **Напоминания** — мультивыбор (каждое = отдельный будильник, независимо); «За день» сам
  по себе ≠ «в момент события».
- **Синхронизация с телефоном** — выбран путь «сначала экспорт»: контакты (vCard + прямой
  импорт в Контакты), события (CalendarContract, односторонне). Полный SyncAdapter НЕ делаем.

## 11. Работа над ошибками — что реально ломалось и как починено (сессия 2026-06)

- **Room identity-hash краш** → version 6→7 + no-op миграция (данные целы).
- **Новый контакт терял телефоны/email** (писались с `contactId="new"`) → `editedContactId`.
- **Связь контакт↔компания** для нового контакта → orphan (рандомный UUID) → `editedContactId` + sync.
- **BootReceiver** без `goAsync()` → напоминания не восстанавливались после reboot.
- **getNotificationId** hash-коллизии; `offsetValue==null` и 29 февраля тихо роняли напоминание.
- **Карта** открывалась на первом адресе (др. город) → центр на last-known локации; пины/легенда
  приведены к одному набору цветов.
- **Фильтры контактов тормозили** → локальное состояние в шторке, пуш по «Применить».
- **Двойной поиск** на Главной/Контактах (капсула + поле в TopAppBar) → прячем капсулу/лупу при активном поиске.
- **«Недавно добавленные»** карточки прыгали по высоте → фикс высоты 140dp.
- **Подарки:** дублирование слова «Размеры» → кнопка только когда размеров нет, иначе карандаш у секции.
- **Форма события** перегружена → Apple inset-list, тип = строка+пикер, барабан даты/времени.
- **Повтор** показывал сырой `FREQ=YEARLY` → русский лейбл.
- **wipeAllData** глотал ошибки → при сбое БД in-memory НЕ чистится; нет ложного «удалено».
- **openWebsite** без whitelist → только http/https.
- **qa_check** пропускал `}!!` → regex чинён.
- **Свои `!!`** в lastKnownLatLng и wheel-пикере убраны.
- **Дубли контактов** → поиск + слияние (Настройки → «Поиск дублей»).
- **«Пропала» функция связей** — НЕ пропала: кнопка добавления в Обзоре видна только в режиме
  редактирования, блок «Связанные люди» скрыт при пустом списке (вопрос обнаруживаемости).

### 2026-07-02 — редизайн Aurelia, разбор жалоб владельца (см. §14/§21 — обязательны к прочтению перед след. правкой UI)

Владелец: «ты уже месяц ставишь дизайн и всё никак», «текстовые поля их нету, что ты сделал»,
«отступ растёт». Разбор по фактам — что было не так и что теперь ПРАВИЛО:

- **Кнопки «+Добавить» были спрятаны за `if (editing)`** (OverviewTab F/O/R/D) — ТОЧНО тот же
  класс бага, что уже был записан выше в этом разделе («пропала функция связей»)! Т.е. этот баг
  УЖЕ был в базе знаний, но я его не сверил перед новой правкой и воспроизвёл вариацию. **Правило:
  перед тем как оставлять новую кнопку/поле за условием `if (editing)`/`if (X)`, явно проверять
  по живому макету — есть ли там вообще отдельный режим правки, или добавление видно сразу.**
  §14 описывает СТАРЫЙ паттерн «Изменить/Готово» как обязательный дефолт — это верно НЕ для
  каждой вкладки; в живом макете Aurelia кнопка «+Добавить факт» в Обзоре видна ВСЕГДА, без
  режима правки вообще (см. поправку в §14).
- **Задвоенный отступ** — добавил новый `item{}` в `LazyColumn` со своим `Modifier.padding(...)`,
  не проверив, что у самого `LazyColumn` уже есть `verticalArrangement = Arrangement.spacedBy(12.dp)`
  — отступы сложились. **Правило: перед тем как добавлять `padding`/`Spacer` вокруг НОВОГО `item{}`,
  прочитать родительский `LazyColumn`/`Column` на `verticalArrangement`/`contentPadding` — если там
  уже есть `spacedBy`, свой отступ на новом item обычно не нужен.**
- **Текст-подсказка нечитаемым цветом** — `FordEmptyHint` использовал `AppleTheme.colors.separator`
  (цвет волосяных РАЗДЕЛИТЕЛЕЙ, ~8% альфа) как цвет ТЕКСТА — почти невидим. Старый баг, найден
  только сейчас. **Правило: `separator`/`divider`-токены — только для линий/бордеров, никогда для
  текста; для приглушённого читаемого текста — `secondaryLabel`/`tertiaryLabel`.**
- **Заявил «собралось и прошло QA», реальная сборка владельца упала** — `MaterialTheme(colorScheme=
  aureliaColorScheme(...))` с ~33 именованными параметрами `lightColorScheme/darkColorScheme`
  ломал компиляцию Kotlin (см. §5/лесенка ниже, лесс. 55). У меня локально compileDebugKotlin
  прошёл «чисто» (пустой вывод) — вероятно инкрементальная/кэшированная компиляция скрыла ошибку.
  **Правило: перед тем как писать «собралось», особенно после КРУПНОЙ/системной правки
  (тема, DI-граф, что-то, что трогает ВЕСЬ проект разом) — гонять `compileDebugKotlin` с нуля
  (`--rerun-tasks` или после `clean`) хотя бы один раз, не доверять пустому выводу после серии
  мелких правок в одном файле.**
- **Системный баг (MaterialTheme без colorScheme) чинился ПОШТУЧНО 3+ раза** (Контакты →
  FilterChip, Дубликаты → Button, Заметки → снова) прежде чем я заметил закономерность и
  исправил в корне. **Правило: если ОДИН И ТОТ ЖЕ класс бага всплывает на 3-м файле подряд —
  СТОП, искать корень/системную причину вместо очередного точечного патча.** См. §21 чек-лист.

## 14. ГЛАВНЫЙ дизайн-паттерн — «Просмотр / Изменить» на КАЖДУЮ вкладку (как iOS Контакты)

Это основа всего редактирования в карточке контакта и компании.

**Просмотр (по умолчанию):**
- Вкладка чистая, только для чтения. Никаких ×, +, карандашей, рамок полей.
- Показываются ТОЛЬКО заполненные поля/блоки. Пустые — НЕ показываются (никаких «Нет данных»).
- Тап по значению = естественное действие (телефон→звонок, адрес→карта, имя→переход), не правка.

**Изменить:**
- Справа вверху вкладки — ОДНА кнопка-текст «Изменить» (iOS-стиль, без карандаша).
- Тап → вся вкладка редактируется инлайн: поля становятся вводом на месте; под списком —
  тихая `AddRow` (зелёный ＋ + подпись, только в правке); удаление — красный `RemoveRow` (－,
  с подтверждением); пустые блоки становятся точками ввода (видны все возможности).
- Кнопка справа → «Готово» (сохранить), слева → «Отмена» (откатить).
- Уровень — ВКЛАДКА (не весь контакт, не отдельный элемент). Переходы плавные (fade/expand).

**Драфт-механика:** при входе в правку — копия контакта (draft) в state; «Готово» →
`updateContact(draft)`; «Отмена» → выбросить draft. Одна схема для всех вкладок.
Переиспользуемые: `TabEditBar`, `AddRow`, `RemoveRow`.

**Запрещено (плохо было):** иконки-действия на каждом элементе в просмотре · карандаши как
способ правки · крупные текст-кнопки правки в просмотре · «Нет данных» · пять ярких кнопок ·
скрытые необозначенные функции · одно действие выглядит по-разному на разных экранах.

**Эргономика iOS:** «Назад» — верх-лево; «Изменить/Готово» — верх-право; создание в списке —
FAB снизу-право. Выбор из многих (контакт/компания) — Bottom Sheet с поиском сверху + «Создать
новый». Авто-заглавная: имена/адрес — по словам; тексты — с заглавной; email/логин/поиск/ссылки/
индекс — без.

**8 вопросов ДО кода:** 1) цель/сценарий 2) точка входа 3) полный поток
(вход→ввод→подтверждение→результат→отмена) 4) все состояния 5) минимум шагов (что предзаполнить)
6) обратная связь (успех/ошибка) 7) край/защита (пусто/дубль/длинный текст/удаление с подтв.)
8) какой готовый паттерн взять.

**⚠️ ПОПРАВКА (2026-07-02): этот паттерн — не универсальный дефолт.** Живой макет Aurelia
для OverviewTab показал кнопку «+ Добавить факт» ВИДИМОЙ ВСЕГДА, без отдельного режима
«Изменить/Готово» вообще — макет просто не различает «просмотр» и «правку» для добавления новых
фактов (F/O/R/D). Старое правило «AddRow только в правке» подходит НЕ для каждой вкладки/секции —
**перед тем как прятать кнопку добавления за `if (editing)`, сверяться с живым макетом ЭТОЙ
конкретной секции**, а не применять §14 механически. (Разбор случая — §11, 2026-07-02.)
Существующий инлайн-режим «Изменить/Готово» (`TabEditBar`, drift-механика) остаётся верным
паттерном для СТРУКТУРИРОВАННЫХ операций (поиск+привязка контакта/компании, множественное
удаление) — просто кнопка «добавить» сама по себе не обязана быть за этим гейтом.

## 15. Проверенные шаблоны исправлений (применять дословно)

1. **`@Composable invocations can only happen from a @Composable function`** — `stringResource`/
   `label()`/`title()` вызваны вне composable (в `.map/.find/.joinToString`, колбэке, `LaunchedEffect`,
   `launch/withContext`, `remember`, или обычной функции). Фикс: `label(context)` через `getString`;
   для `stringResource` в корутине — захватить в `val` ДО эффекта.
2. **`Unresolved reference 'ctxLabel'`** — у каждой функции свой контекст. В `@Composable` —
   `val ctxLabel = LocalContext.current` в начале. В `LazyListScope`-расширении (`fun LazyListScope.xxxTab`,
   НЕ composable) — параметр `ctxLabel: Context`. Импорт `androidx.compose.ui.platform.LocalContext`.
3. **`Invalid unicode escape` / `not a valid string resource`** — это `mergeDebugResources`, не Kotlin.
   Неэкранированный символ в strings.xml: `'`→`\'`, `&`→`&amp;`. Чинить в 3 локалях. Искать по ИМЕНИ ресурса.
4. **Чтение enum из БД — только через `safeEnum`** (из `Mappers.kt`), НЕ `Enum.valueOf` напрямую
   (кривое значение из импорта роняет `reloadFromDb`):
   `inline fun <reified T:Enum<T>> safeEnum(v:String?, def:T):T = v?.let{runCatching{enumValueOf<T>(it)}.getOrNull()} ?: def`
5. **Схема БД изменилась → version++ + Migration** (`allowBackup="false"`, иначе старая .db вернётся из облака).
6. **`This material API is experimental`** → `@OptIn(ExperimentalMaterial3Api::class)` (+ `ExperimentalLayoutApi` для FlowRow).

**Никакой логики на тексте строки.** Тип/статус/режим/повтор/единицы — на `when(enum)`, фильтры —
на enum/флаге, табы — на индексе. После перевода лейбла логика обязана работать без изменений.
Обратный матчинг дропдаунов `firstOrNull { it.label(ctx)==v }` безопасен ТОЛЬКО при уникальных лейблах.

**НЕ переименовывать** переменные/функции «для чистоты» — создаёт `Unresolved reference` в других файлах.

## 20. Безопасность — постоянный чек-лист и работа над ошибками

> Источник: cybersecurity-скиллы `exploiting-insecure-data-storage-in-mobile`,
> `conducting-mobile-app-penetration-test`, `exploiting-deeplink-vulnerabilities`.
> Прогонять ПЕРЕД релизом и при любой работе с хранением/интентами/экспортом.

**Модель угроз нашего приложения:** локальный однопользовательский CRM без сервера и
аутентификации. Основной риск — **физический/ADB/рутованный доступ к устройству** и
**чужой импортируемый файл** (бэкап/визитка). Не «удалённый взлом», а «доступ к данным на руках».

**Стоячий чек-лист (что проверять):**
- [ ] **PII НИКОГДА не логировать** (`Log.*` с именами/телефонами/email/заметками). logcat читаем.
- [ ] **Любой внешний `Uri.parse → ACTION_VIEW`/intent** — только с whitelist схем
      (http/https и явный список). Блок `file:`/`content:`/`intent:`/`javascript:`/`data:`.
      Поля сайта/мессенджера/ссылки могут прийти из чужого бэкапа.
- [ ] **Экспорт PII** (vCard/JSON/CSV/ZIP) — temp-файлы короткоживущие, чистить из cacheDir,
      не оставлять навсегда.
- [ ] **`android:allowBackup="false"`** (иначе ADB-бэкап вытащит БД).
- [ ] **Нет WebView** (а если появится — без `setJavaScriptEnabled(true)`/`addJavascriptInterface`).
- [ ] **Exported-компоненты** — `exported="false"` кроме launcher и BootReceiver (тому нужен
      BOOT_COMPLETED; он только пере-планирует из БД, чужих данных не принимает).
- [ ] **FileProvider** — `exported="false"` + `grantUriPermissions`, отдавать только нужный uri.
- [ ] **Maps API key** — обязательно restrict по **package + SHA-1** в Google Cloud (ключ в APK,
      без ограничения = кража квоты).
- [ ] **Release-keystore НИКОГДА не коммитить** (debug.keystore — стандартный публичный, ок).
- [ ] **Импорт бэкапа** — проверять формат/версию (не доверять чужому JSON вслепую).
- [ ] **Чтение enum из БД/импорта** — только `safeEnum` (кривое значение роняет reloadFromDb).

**Сделано (работа над ошибками по скиллам, 2026-06):**
- `openWebsite` — whitelist http/https.
- `openMessenger` — whitelist схем (http/https/tg/viber/whatsapp/sgnl/mailto/tel), блок file/intent/…
- Экспорт — `cleanOldExports()` чистит прошлые temp-файлы PII из cacheDir перед каждым экспортом.
- backup-restore — проверка `version ∈ 1..5`.
- allowBackup=false ✅, нет WebView ✅, нет сетевой поверхности (Retrofit/OkHttp не используются) ✅,
  нет входящих deeplink ✅, PII в логах нет ✅.

**Открыто (для машины владельца — здесь среда офлайн, новые зависимости не качаются):**
- 🔴 **Шифрование БД (SQLCipher)** — сейчас Room хранит всю персоналку в ОТКРЫТОМ SQLite.
  План: добавить `net.zetetic:android-database-sqlcipher` + `androidx.sqlite:sqlite-ktx`,
  ключ хранить в **Android Keystore** (не хардкодить, не класть рядом с БД),

## 21. Чек-лист перед сдачей UI/редизайн-правки (родился из провалов 2026-07-02 — обязателен)

`qa_check.py` зелёный ловит статические баги (импорты, хардкод, force-unwrap), но НЕ ловит эти —
их проверяю руками, каждый раз, перед тем как писать «готово»/«собралось»:

1. **Обнаруживаемость.** Для каждой новой кнопки/поля пройти путь глазами С НУЛЯ: сколько тапов
   от открытия вкладки до этого элемента? Если ответ включает «сначала войти в режим правки» —
   явно решить (и написать в ответе пользователю), это так задумано или баг обнаруживаемости
   (§11 2026-07-02, §14 поправка).
2. **Отступы нового item.** Добавляя `item{}` в существующий `LazyColumn`/`Column` — прочитать его
   `verticalArrangement`/`contentPadding` ПЕРЕД тем, как вешать свой `Modifier.padding` на новый
   элемент. Если уже есть `spacedBy(N.dp)`, свой отступ на новом item, скорее всего, лишний (У57).
3. **Семантика цветового токена.** `separator`/`divider`/`outline*` — только для линий/бордеров.
   Если это цвет ТЕКСТА — брать `secondaryLabel`/`tertiaryLabel`, даже если «на глаз» похоже,
   что подойдёт (У56).
4. **Системный повтор бага.** Если один и тот же класс ошибки (не буква в букву, а СУТЬ) чинится
   уже в 3-м файле подряд за сессию — остановиться и поискать корень/точку с одним источником
   правды, вместо 4-го точечного патча.
5. **Свежая сборка после крупной правки.** Правка темы/DI/чего-то общего на весь проект —
   собрать `compileDebugKotlin` заново (после `clean` или `--rerun-tasks`), не доверять пустому
   выводу инкрементальной компиляции как единственному подтверждению (У59). Для функций с ~30+
   именованными аргументами (M3 `ColorScheme`-билдеры и подобные) — см. У55, сверять с рабочим
   примером в проекте, а не собирать полный список полей из документации.
6. **Живой макет как единственный источник правды по стилю, но НЕ по паттернам взаимодействия
   вслепую.** §14 фиксирует общий паттерн «Просмотр/Изменить» — он не отменяет необходимость
   свериться с макетом ИМЕННО этой секции перед тем, как гейтить новую кнопку добавления за
   `editing`. Разные вкладки/секции макета могут вести себя по-разному (см. поправку в §14).
