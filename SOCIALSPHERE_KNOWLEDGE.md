## 2. Запрещено ВСЕГДА (жёсткие правила)

- `!!` (force-unwrap) и `database!!` — только безопасный доступ (`?:`, `val x = nullable`)
- `resolveActivity()` (Android 11+ возвращает null) — `startActivity` в try-catch
- хардкод UI-строк при наличии ресурса — только `stringResource`, сразу в **3** strings.xml
- `enum.name` в UI — только `.label(context)`
- `mutableStateOf` для настроек — только `PersistedMutableState` (диск)
- `LocalDate.now().toString()` для datetime-полей — нужен ISO_LOCAL_DATE_TIME
- пустые `onClick = {}` / `onCheckedChange = {}` — обманка хуже отсутствия контрола
- `kotlinOptions { }` — только `kotlin { compilerOptions { } }`
- свитч/контрол без реального поля в модели — обманка, удалять
- переписывать файл целиком по «улучши/почини» — только точечные правки

## 3. Рабочий цикл и дисциплина (нарушение = повтор старых ошибок)

1. **Один шаг = одна вещь.** Никаких «заодно».
2. **Сначала читай реальный код** (свежий grep/Read), потом пиши. Якоря — только из
   свежего вывода, НЕ из памяти. Проверяй сигнатуры, имена enum-значений, состав object,
   что private/public **перед** использованием.
3. **Если правка не нашла якорь — СТОП, перечитай.** Не угадывать повторно.
4. **Реестр ограничений:** перед UI-правкой выписать «делать/не делать» из последних
   сообщений пользователя, сверить (пример: «убрать стрелки» = не возвращать шевроны).
5. **Сохранность функций:** не переписывать блок, не перечислив все его функции и не
   подтвердив, что каждая сохранена.
6. **Анти-хардкод:** после UI-правки grep участка на строковые литералы без `R.string`.
7. **`qa_check.py` ЗЕЛЁНЫЙ перед каждой выдачей.** (см. §9 — как запускать в этой среде)
8. **Первая `e:`-строка компилятора важнее десяти статических догадок.** Цикл:
   сборка → первая ошибка → фикс → сборка. `finished` + warning ≠ провал; паниковать
   только на `failed` + `e:`.
9. **Правило от 2026-07-06/07 (владелец сказал прямо: «ты больше не отговаривался а делал все
   проверки») — для ЛЮБОЙ UI-фичи (тумблер, экран, диалог, тап-путь) «собралось + `qa_check.py`
   зелёный + юнит-тесты прошли» — это НЕ «готово», это только первая треть пути.** Готово —
   только после реальной проверки на эмуляторе: `adb install` собранного debug-APK →
   `adb shell input tap`/`uiautomator dump` по реальным экранам → скриншот как доказательство.
   Окружение для этого уже собрано на машине (Android SDK, `cmdline-tools`, `system-images;
   android-35;google_apis;x86_64`, AVD `test_avd`) — «нет эмулятора» отныне НЕ повод пропустить
   этот шаг, это одноразовая настройка, которая уже сделана. Отсутствие визуальной проверки —
   не оговорка в конце отчёта, а СТОП-сигнал не объявлять фичу законченной.

## 6. Архитектурные инварианты (наработаны и проверены)

- **Интенты** — только `ExternalActionHandler.startIntentSafely` (локализованный
  контекст ≠ Activity; прямой startActivity молча падает).
- **Дни рождения / FREQ=YEARLY** — в отображении только через `effectiveDate()`
  (utils/CalendarUtils.kt); сырые даты прошлого невидимы навсегда. В детали повтор
  показывать через `RecurrenceMode.fromRule()` (не сырой RRULE «FREQ=YEARLY»).
- **lastContactDate** — date-only `.take(10)` при записи И чтении.
- **Размеры** — только `AppStateStore.setSizeInfo()` (синхронизирует 3 места);
  `updateNote` НЕ трогает lastContactDate.
- **Тяжёлые filter/sorted/groupBy** — в `remember { derivedStateOf }`; пер-строчные — `remember(id)`.
- **Тяжёлые экраны с мультивыбором** (фильтры) — локальное состояние в листе/шторке,
  пуш к родителю по «Применить»/закрытию, иначе пересчёт списка на каждый тап тормозит.
- **Скролл-контейнер под шапкой/табами в Column** — `Modifier.weight(1f)`, НЕ `fillMaxSize()`
  (иначе прокрутка схлопывается до полэкрана — баг ловился 3+ раза).
- **Настройки** — каждый контрол пишет в `AppSettings` (PersistedMutableState) и реально меняет.
- **Manifest** — `configChanges` на MainActivity не удалять (поворот стирал формы);
  `android:enableOnBackInvokedCallback="true"` на `<application>`.
- **GoogleMap** — только после проверки Google Play Services; `cameraState.animate()`
  в try-catch; `isMyLocationEnabled` только при выданном разрешении.
- **BroadcastReceiver с async-работой** (BootReceiver) — `goAsync()` + `pendingResult.finish()`,
  иначе процесс убьют до конца корутины (напоминания не восстановятся после reboot).
- **Новый контакт** — телефоны/email/мессенджеры/связи писать с `editedContactId`,
  НЕ с `"new"` и НЕ с новым случайным UUID (иначе данные/связи теряются).
- **addContact** — синхронизировать ГЛОБАЛЬНЫЕ `addresses`/`companyRelations` сразу
  (как `updateContact`), иначе связь контакт↔компания и адреса на карте не видны до перезапуска.

## 7. База данных и сохранность (критично)

- Текущая БД **version = 7**, миграции 1→7 прописаны, `exportSchema=true` (схемы в `app/schemas/`).
- При добавлении/изменении @Entity — **обязательно** version++ И миграция (даже no-op,
  если SQL не менялся, но identity-hash разошёлся).
- Удаление приложения стирает БД → обновляться **установкой поверх**.
- Перед обновлением/слиянием дублей — «Сохранить JSON» (полный бэкап). Восстановление —
  upsert по id (ничего не удаляет, сохраняет createdAt). Импорт бэкапа проверяет `version ∈ 1..5`.
- Краш `Room cannot verify data integrity (identity hash)` = схема изменилась без version++.
- destructive fallback — ТОЛЬКО в debug; в release падать явно, не стирать данные.

## 8. Дизайн-система и принципы (уровень Apple — для всего)

- **Цвета по смыслу:** `primary #4F3DC7` — действия/акценты; `tertiary` — даты/события;
  `error` — просрочка/опасное; `secondary` — второстепенный текст.
- **Карта/легенда:** дом = синий, работа = зелёный, компания = фиолетовый, выбранный = оранжевый —
  цвета маркеров, легенды и списка ДОЛЖНЫ совпадать.
- **Формы SocialShape:** поля/чипы 8, карточки 16, bottom sheet 24, аватары/бейджи 50%.
  Отступы кратны 4dp.
- **Apple-форма (сложные экраны):** сгруппированный inset-list компактных строк
  (слева подпись, справа значение серым + шеврон). Тип/выбор = ОДНА строка → пикер,
  НЕ сетка чипов на пол-экрана. Не прятать нужное под «Подробнее» с гигантским скроллом.
- **Дата/время:** только пикерами (барабан-wheel + пресеты «Сегодня/Завтра»), не ручным вводом.
- **Обнаруживаемость:** пустое состояние = точка входа («+ Добавить …», не «Нет данных»);
  действие — в заголовке блока; один акцент на экран; подпись у неочевидных иконок;
  редактирование — тапом по блоку, не мелким карандашом.
- **Эргономика:** тап-цели ≥48dp; частое — в зоне большого пальца; живую карту не класть
  в общий скролл (фикс. высота).

## 10. Продуктовые решения (смысловые)

- **ImportanceLevel:** обычный → важный → ключевой (топ-приоритетные люди).
- **FORD «Семья» vs «Связанные люди»:** «Семья» = семейные роли; «Связанные люди» в Обзоре =
  только НЕсемейные. Роли с обеих сторон (firstRole=моя, secondRole=его). Добавление связей —
  в Обзоре в режиме редактирования И в форме контакта (секция «Семья и отношения»).
- **Событие на нескольких людей** — `links` список; UI = мультивыбор.
- **Подарки** — один источник правды = вкладка «Подарки» (`GiftIdea`, IDEA→BOUGHT→GIVEN).
- **«Где познакомились»** — в «Обзоре». **Адреса:** рабочие → «Работа», дом/прочее → «Связь»
  (и на карте: личные на вкладке «Контакты», рабочие — на «Работа»).
- **Телефоны** дедуплицируются по последним 10 цифрам.
- **Напоминания** — мультивыбор (каждое = отдельный будильник, независимо); «За день» сам
  по себе ≠ «в момент события».
- **Синхронизация с телефоном** — выбран путь «сначала экспорт»: контакты (vCard + прямой
  импорт в Контакты), события (CalendarContract, односторонне). Полный SyncAdapter НЕ делаем.

## 11. Работа над ошибками — что реально ломалось и как починено (сессия 2026-06)

- **Room identity-hash краш** → version 6→7 + no-op миграция (данные целы).
- **Новый контакт терял телефоны/email** (писались с `contactId="new"`) → `editedContactId`.
- **Связь контакт↔компания** для нового контакта → orphan (рандомный UUID) → `editedContactId` + sync.
- **BootReceiver** без `goAsync()` → напоминания не восстанавливались после reboot.
- **getNotificationId** hash-коллизии; `offsetValue==null` и 29 февраля тихо роняли напоминание.
- **Карта** открывалась на первом адресе (др. город) → центр на last-known локации; пины/легенда
  приведены к одному набору цветов.
- **Фильтры контактов тормозили** → локальное состояние в шторке, пуш по «Применить».
- **Двойной поиск** на Главной/Контактах (капсула + поле в TopAppBar) → прячем капсулу/лупу при активном поиске.
- **«Недавно добавленные»** карточки прыгали по высоте → фикс высоты 140dp.
- **Подарки:** дублирование слова «Размеры» → кнопка только когда размеров нет, иначе карандаш у секции.
- **Форма события** перегружена → Apple inset-list, тип = строка+пикер, барабан даты/времени.
- **Повтор** показывал сырой `FREQ=YEARLY` → русский лейбл.
- **wipeAllData** глотал ошибки → при сбое БД in-memory НЕ чистится; нет ложного «удалено».
- **openWebsite** без whitelist → только http/https.
- **qa_check** пропускал `}!!` → regex чинён.
- **Свои `!!`** в lastKnownLatLng и wheel-пикере убраны.
- **Дубли контактов** → поиск + слияние (Настройки → «Поиск дублей»).
- **«Пропала» функция связей** — НЕ пропала: кнопка добавления в Обзоре видна только в режиме
  редактирования, блок «Связанные люди» скрыт при пустом списке (вопрос обнаруживаемости).

### 2026-07-02 — редизайн Aurelia, разбор жалоб владельца (см. §14/§21 — обязательны к прочтению перед след. правкой UI)

Владелец: «ты уже месяц ставишь дизайн и всё никак», «текстовые поля их нету, что ты сделал»,
«отступ растёт». Разбор по фактам — что было не так и что теперь ПРАВИЛО:

- **Кнопки «+Добавить» были спрятаны за `if (editing)`** (OverviewTab F/O/R/D) — ТОЧНО тот же
  класс бага, что уже был записан выше в этом разделе («пропала функция связей»)! Т.е. этот баг
  УЖЕ был в базе знаний, но я его не сверил перед новой правкой и воспроизвёл вариацию. **Правило:
  перед тем как оставлять новую кнопку/поле за условием `if (editing)`/`if (X)`, явно проверять
  по живому макету — есть ли там вообще отдельный режим правки, или добавление видно сразу.**
  §14 описывает СТАРЫЙ паттерн «Изменить/Готово» как обязательный дефолт — это верно НЕ для
  каждой вкладки; в живом макете Aurelia кнопка «+Добавить факт» в Обзоре видна ВСЕГДА, без
  режима правки вообще (см. поправку в §14).
- **Задвоенный отступ** — добавил новый `item{}` в `LazyColumn` со своим `Modifier.padding(...)`,
  не проверив, что у самого `LazyColumn` уже есть `verticalArrangement = Arrangement.spacedBy(12.dp)`
  — отступы сложились. **Правило: перед тем как добавлять `padding`/`Spacer` вокруг НОВОГО `item{}`,
  прочитать родительский `LazyColumn`/`Column` на `verticalArrangement`/`contentPadding` — если там
  уже есть `spacedBy`, свой отступ на новом item обычно не нужен.**
- **Текст-подсказка нечитаемым цветом** — `FordEmptyHint` использовал `AppleTheme.colors.separator`
  (цвет волосяных РАЗДЕЛИТЕЛЕЙ, ~8% альфа) как цвет ТЕКСТА — почти невидим. Старый баг, найден
  только сейчас. **Правило: `separator`/`divider`-токены — только для линий/бордеров, никогда для
  текста; для приглушённого читаемого текста — `secondaryLabel`/`tertiaryLabel`.**
- **Заявил «собралось и прошло QA», реальная сборка владельца упала** — `MaterialTheme(colorScheme=
  aureliaColorScheme(...))` с ~33 именованными параметрами `lightColorScheme/darkColorScheme`
  ломал компиляцию Kotlin (см. §5/лесенка ниже, лесс. 55). У меня локально compileDebugKotlin
  прошёл «чисто» (пустой вывод) — вероятно инкрементальная/кэшированная компиляция скрыла ошибку.
  **Правило: перед тем как писать «собралось», особенно после КРУПНОЙ/системной правки
  (тема, DI-граф, что-то, что трогает ВЕСЬ проект разом) — гонять `compileDebugKotlin` с нуля
  (`--rerun-tasks` или после `clean`) хотя бы один раз, не доверять пустому выводу после серии
  мелких правок в одном файле.**
- **Системный баг (MaterialTheme без colorScheme) чинился ПОШТУЧНО 3+ раза** (Контакты →
  FilterChip, Дубликаты → Button, Заметки → снова) прежде чем я заметил закономерность и
  исправил в корне. **Правило: если ОДИН И ТОТ ЖЕ класс бага всплывает на 3-м файле подряд —
  СТОП, искать корень/системную причину вместо очередного точечного патча.** См. §21 чек-лист.

## 14. ГЛАВНЫЙ дизайн-паттерн — «Просмотр / Изменить» на КАЖДУЮ вкладку (как iOS Контакты)

Это основа всего редактирования в карточке контакта и компании.

**Просмотр (по умолчанию):**
- Вкладка чистая, только для чтения. Никаких ×, +, карандашей, рамок полей.
- Показываются ТОЛЬКО заполненные поля/блоки. Пустые — НЕ показываются (никаких «Нет данных»).
- Тап по значению = естественное действие (телефон→звонок, адрес→карта, имя→переход), не правка.

**Изменить:**
- Справа вверху вкладки — ОДНА кнопка-текст «Изменить» (iOS-стиль, без карандаша).
- Тап → вся вкладка редактируется инлайн: поля становятся вводом на месте; под списком —
  тихая `AddRow` (зелёный ＋ + подпись, только в правке); удаление — красный `RemoveRow` (－,
  с подтверждением); пустые блоки становятся точками ввода (видны все возможности).
- Кнопка справа → «Готово» (сохранить), слева → «Отмена» (откатить).
- Уровень — ВКЛАДКА (не весь контакт, не отдельный элемент). Переходы плавные (fade/expand).

**Драфт-механика:** при входе в правку — копия контакта (draft) в state; «Готово» →
`updateContact(draft)`; «Отмена» → выбросить draft. Одна схема для всех вкладок.
Переиспользуемые: `TabEditBar`, `AddRow`, `RemoveRow`.

**Запрещено (плохо было):** иконки-действия на каждом элементе в просмотре · карандаши как
способ правки · крупные текст-кнопки правки в просмотре · «Нет данных» · пять ярких кнопок ·
скрытые необозначенные функции · одно действие выглядит по-разному на разных экранах.

**Эргономика iOS:** «Назад» — верх-лево; «Изменить/Готово» — верх-право; создание в списке —
FAB снизу-право. Выбор из многих (контакт/компания) — Bottom Sheet с поиском сверху + «Создать
новый». Авто-заглавная: имена/адрес — по словам; тексты — с заглавной; email/логин/поиск/ссылки/
индекс — без.

**8 вопросов ДО кода:** 1) цель/сценарий 2) точка входа 3) полный поток
(вход→ввод→подтверждение→результат→отмена) 4) все состояния 5) минимум шагов (что предзаполнить)
6) обратная связь (успех/ошибка) 7) край/защита (пусто/дубль/длинный текст/удаление с подтв.)
8) какой готовый паттерн взять.

**⚠️ ПОПРАВКА (2026-07-02): этот паттерн — не универсальный дефолт.** Живой макет Aurelia
для OverviewTab показал кнопку «+ Добавить факт» ВИДИМОЙ ВСЕГДА, без отдельного режима
«Изменить/Готово» вообще — макет просто не различает «просмотр» и «правку» для добавления новых
фактов (F/O/R/D). Старое правило «AddRow только в правке» подходит НЕ для каждой вкладки/секции —
**перед тем как прятать кнопку добавления за `if (editing)`, сверяться с живым макетом ЭТОЙ
конкретной секции**, а не применять §14 механически. (Разбор случая — §11, 2026-07-02.)
Существующий инлайн-режим «Изменить/Готово» (`TabEditBar`, drift-механика) остаётся верным
паттерном для СТРУКТУРИРОВАННЫХ операций (поиск+привязка контакта/компании, множественное
удаление) — просто кнопка «добавить» сама по себе не обязана быть за этим гейтом.

## 15. Проверенные шаблоны исправлений (применять дословно)

1. **`@Composable invocations can only happen from a @Composable function`** — `stringResource`/
   `label()`/`title()` вызваны вне composable (в `.map/.find/.joinToString`, колбэке, `LaunchedEffect`,
   `launch/withContext`, `remember`, или обычной функции). Фикс: `label(context)` через `getString`;
   для `stringResource` в корутине — захватить в `val` ДО эффекта.
2. **`Unresolved reference 'ctxLabel'`** — у каждой функции свой контекст. В `@Composable` —
   `val ctxLabel = LocalContext.current` в начале. В `LazyListScope`-расширении (`fun LazyListScope.xxxTab`,
   НЕ composable) — параметр `ctxLabel: Context`. Импорт `androidx.compose.ui.platform.LocalContext`.
3. **`Invalid unicode escape` / `not a valid string resource`** — это `mergeDebugResources`, не Kotlin.
   Неэкранированный символ в strings.xml: `'`→`\'`, `&`→`&amp;`. Чинить в 3 локалях. Искать по ИМЕНИ ресурса.
4. **Чтение enum из БД — только через `safeEnum`** (из `Mappers.kt`), НЕ `Enum.valueOf` напрямую
   (кривое значение из импорта роняет `reloadFromDb`):
   `inline fun <reified T:Enum<T>> safeEnum(v:String?, def:T):T = v?.let{runCatching{enumValueOf<T>(it)}.getOrNull()} ?: def`
5. **Схема БД изменилась → version++ + Migration** (`allowBackup="false"`, иначе старая .db вернётся из облака).
6. **`This material API is experimental`** → `@OptIn(ExperimentalMaterial3Api::class)` (+ `ExperimentalLayoutApi` для FlowRow).

**Никакой логики на тексте строки.** Тип/статус/режим/повтор/единицы — на `when(enum)`, фильтры —
на enum/флаге, табы — на индексе. После перевода лейбла логика обязана работать без изменений.
Обратный матчинг дропдаунов `firstOrNull { it.label(ctx)==v }` безопасен ТОЛЬКО при уникальных лейблах.

**НЕ переименовывать** переменные/функции «для чистоты» — создаёт `Unresolved reference` в других файлах.

## 20. Безопасность — постоянный чек-лист и работа над ошибками

> Источник: cybersecurity-скиллы `exploiting-insecure-data-storage-in-mobile`,
> `conducting-mobile-app-penetration-test`, `exploiting-deeplink-vulnerabilities`.

**Модель угроз нашего приложения:** локальный однопользовательский CRM без сервера и
аутентификации. Основной риск — **физический/ADB/рутованный доступ к устройству** и

- [ ] **Нет WebView** (а если появится — без `setJavaScriptEnabled(true)`/`addJavascriptInterface`).

- [ ] **Maps API key** — обязательно restrict по **package + SHA-1** в Google Cloud (ключ в APK,

- [ ] **Release-keystore НИКОГДА не коммитить** (debug.keystore — стандартный публичный, ок).
- [ ] **Импорт бэкапа** — проверять формат/версию (не доверять чужому JSON вслепую).

   примером в проекте, а не собирать полный список полей из документации.
6. **Живой макет как единственный источник правды по стилю, но НЕ по паттернам взаимодействия
   вслепую.** §14 фиксирует общий паттерн «Просмотр/Изменить» — он не отменяет необходимость
   свериться с макетом ИМЕННО этой секции перед тем, как гейтить новую кнопку добавления за
   `editing`. Разные вкладки/секции макета могут вести себя по-разному (см. поправку в §14).
7. **Пересборка сущности на сохранении.** Если правится/сохраняется уже существующая сущность
   (место работы, адрес, контакт) — использовать `copy()` оригинала, НЕ пересобирать конструктор
   с нуля с хардкод-дефолтами. Иначе поля, не упомянутые явно в новом конструкторе, стираются на
   каждое сохранение (У60) — самый дорогой класс бага в этой сессии, повторился дважды.
8. **Новая сущность/поле — аудит графа целиком.** Добавили `@Entity`/новое поле в `Contact` —
   грепнуть не только `Mappers.kt`, но и `BackupData`/`buildAndSave`/`mergeContacts`/везде, где
   обходится весь набор данных контакта (У61).
9. **Флаг с 2+ точками чтения/записи.** Правя проверку разрешения/состояния — грепнуть ВСЕ места,
   где этот же флаг устанавливается или читается (начальная проверка при старте, launcher-коллбэк,
   место использования). Правка одной точки при рассинхроне с другой — фикс, который не работает,
   но выглядит рабочим, потому что компилируется (У67).
10. **Глобальный modifier на shared-обёртку (`NavHost`/внешний `Scaffold`) — проверить соседей
    дерева.** Прежде чем считать fix готовым, спросить: что ЕЩЁ есть в этом дереве, что тоже
    подвержено эффекту правки (постоянный nav bar, шапка, etc.), и не создаёт ли фикс НОВЫЙ баг
    именно там (У68).
11. **«Переведи все X на новый дизайн/паттерн» — сначала полный `grep -rn` по всей кодовой базе,
    список ВСЕХ вхождений, явная классификация каждого, потом проход по списку целиком.** Точечная
    правка одного файла/диалога, который на виду в моменте разговора — не выполнение запроса,
    даже если она чинит реальный баг (скролл/обрезание) внутри старого компонента (У69).

## 22. Работа над ошибками — сессия 2026-07-03/04 (полный разбор фидбэка владельца)

Владелец попросил вывести из истории чата все правки как ошибки-с-причинами и обновить базу

- **Форма контакта стирала `lastContactDate`/`deviceContactId` при КАЖДОЙ правке** — конструктор

- **На вкладке Связь нельзя было сменить тип адреса на «рабочий»** — диалог адреса там был

  Раздвоенная реализация одной механики — расползается по возможностям без единого источника правды.

  обработчик), пережил несколько циклов ревью незамеченным несмотря на запрет §2.
- **Заметки и личные детали нельзя было редактировать после создания** — реализовали Create+Delete,
  Update не предусмотрели.

### Архитектурные

- **Заголовки календарных событий показывались по-гречески при русской локали** — импорт запекал
  локализованную строку (`context.getString(R.string.imp_birthday_of, ...)`) прямо в поле `title`
  в момент импорта; язык устройства на тот момент зафиксировался в данных навсегда. Чинить пришлось
  распознаванием названия типа СРАЗУ во всех языках приложения (`localizedVariants`), не трогая
  уже сохранённые данные. Правило: локализованная строка никогда не идёт в персистентные данные —
  только нейтральный ключ/тип, перевод — при показе.
- **После компактизации контекста доложил, что 9 из 11 пунктов не сделаны** — хотя большинство уже
  было реализовано в предыдущей части сессии. Доверился сводке компактизации вместо повторной
  сверки кода. Стоило дороже времени, чем сама работа над отставшими пунктами.

### Поведенческие (обнаруживаемость и нестабильные решения)

- **«Связать с контактом телефона» — было неясно, что делает.** Действие происходило молча.
  Починено добавлением тостов с результатом («Добавлено: N тел., M email…» / «Уже актуально»).
- **Кнопки добавления FORD прятались/показывались/снова прятались за `if(editing)` — 3 раза
  за проект.** Каждый раз решение выводилось из снимка макета или интуиции о «лучшей практике»,
  а не фиксировалось как явное датированное решение владельца, на которое можно сослаться
  в следующий раз. Стоит явно спрашивать/фиксировать «это окончательно?» для таких развилок.
- **Поле «Статус» — слили с уровнем связи → убрали из UI → вернули.** Тот же паттерн нестабильного
  решения. Смягчающий фактор (сделано верно с первого раза): поле в БД никогда не удалялось,
  трогался только UI — откат обошёлся в несколько правок, а не в миграцию данных.

### Дизайн

- **«Через N дней» у подарка вставало криво сбоку от длинного заголовка.** Переменная по длине
  информация была встык с заголовком в одну строку без учёта переполнения.
- **Двойной отступ сверху на всех экранах.** Внешний Scaffold (MainActivity, обёртка над

  удваивался. Правило: при нескольких вложенных Scaffold — инсет верха применяет ровно один

- **«Ключевой»/«Важный» — разные цвета в списке (было красным) и в карточке (было золотом)
  для ОДНОГО И ТОГО ЖЕ значения enum.** Семантика цвета важности не была вынесена в общий токен —
  каждый экран красил по своему усмотрению. Починено общими токенами `importanceKey`/`importanceHigh`.

### Итоговые правила (сверх уже записанных в §2/§5/§21)

1. Пересобирая сущность на сохранении — `copy()` оригинала, не хардкод-конструктор с нуля (У60).
2. Новая сущность/поле — аудит ВСЕГО графа (БД + бэкап + merge), не только маппера (У61).
3. Локализованная строка никогда не идёт в персистентные данные (У62).
4. Одна UI-механика в 2+ экранах — общий компонент СРАЗУ, не после жалобы (У63).
5. Правило §2 про «пустой onClick» — применять и к ревизии старых контролов, не только к новым (У64).
6. Новый тип записи — предусмотреть Update, не только Create+Delete (У65).
7. После компактизации — сверять сводку с реальным кодом, не доверять вслепую (У66).
8. Нестабильные UI-решения (флип-флоп по одному и тому же полю/кнопке) — фиксировать как явное
   датированное решение владельца в базе знаний, сверяться с ним перед следующей правкой той же
   области, не выводить заново из интуиции/макета.

## 24. Работа над ошибками — сессия 2026-07-05/06 (защита приложения: PIN + блокировка + критичный баг биометрии)

Прямой запрос владельца: проанализировать защиту приложения, настроить биометрию и PIN-коды
«чтобы работали и редактировались в опциях», и отдельно отладить «скрытие данных в контактах»

### Найден критичный баг (не в этой сессии внесён — существовал с момента, когда появился замочек)

**`LocalContext.current as? FragmentActivity` в `ContactDetailScreen.kt` ВСЕГДА возвращал `null`.**
`MainActivity.setContent` оборачивает весь `SocialsphereApp()` в `LocalizedApp(language) { … }`
(`SettingsState.kt`), а `LocalizedApp` подменяет `LocalContext.current` на
`context.createConfigurationContext(config)` — обычный `Context`, НЕ подкласс `Activity`/
`FragmentActivity`. Прямой `as? FragmentActivity` где угодно ниже по дереву композиции молча
даёт `null`. Следствие: ветка биометрии в `requestReveal()` была мёртвым кодом — при тапе
«раскрыть защищённую заметку» код всегда уходил в `else`-ветку и **снимал приватность БЕЗ единого
запроса аутентификации**, при этом UI (иконка замка, блюр, бейдж «Защищено») визуально создавал
полную иллюзию защиты. Обнаружено не рутинным аудитом (§23 его не поймал — тот проверял
синхронизацию permission-флагов, не корректность Activity-cast), а при целевом разборе логики
биометрии по прямому запросу владельца.

**Фикс:** `tailrec fun Context.findActivity(): FragmentActivity?` (`utils/BiometricGate.kt`) —
разматывает `ContextWrapper.baseContext` до настоящей Activity. **Правило на будущее: любой
`LocalContext.current as? SomeActivityType` в этой кодовой базе — подозрительный, искать через
`findActivity()`.** При разборе найден и починен второй экземпляр той же ошибки — диплинк
«открыть календарь из уведомления» в `MainActivity.kt` (`SocialsphereApp()`, строка с
`activity?.intent`) тоже читал `LocalContext.current as? Activity` под тем же `LocalizedApp` —
уведомление никогда не открывало нужную карточку календаря. Оба места переведены на `findActivity()`.

### Построено: свой PIN-код + блокировка всего приложения (новая, отдельная от «Защищено»-биометрии фича)

Раньше единственный способ защиты — биометрия/код УСТРОЙСTBA, и только для заметок с
`isImportant=true`. Не было: (а) защиты, не зависящей от системных настроек экрана блокировки,
(б) блокировки ВСЕГО приложения на запуске.

- **Хранение PIN:** не пароль в открытом виде — соль (16 байт, `SecureRandom`) + хеш
  (`PBKDF2WithHmacSHA256`, 120k итераций) одной строкой `"saltHex:hashHex"` через штатный
  `PersistedMutableState` (`SettingsState.kt`). Чистый `javax.crypto`, без новой Gradle-зависимости
  (среда иногда офлайн для новых библиотек, §9) — сознательно НЕ подключали
  `androidx.security:security-crypto`/`EncryptedSharedPreferences`.
- **`AppLockScreen`** (`ui/screens/AppLockComponents.kt`) — полноэкранный, недисмиссный гейт:
  автозапуск биометрии при показе (если доступна) + собственная PIN-клавиатура как основной/
  резервный способ.
  Показывается в `SocialsphereApp()` (`MainActivity.kt`), ПОСЛЕ онбординга, когда
  `AppSettings.appLockEnabledSafe() && !AppLockState.unlocked`.
- **Grace-период при сворачивании** (30 сек, `APP_LOCK_GRACE_MS`) через
  `LifecycleEventObserver` на `ON_STOP`/`ON_START`: иначе `ExternalActionHandler.startIntentSafely`
  (звонок/SMS/карты) сворачивает приложение внешним интентом и тут же запирал бы его снова.
  `AppLockState` — намеренно НЕ персистентный синглтон (только в памяти процесса): после смерти
  процесса приложение обязано снова спросить PIN/биометрию — это безопасный дефолт, а
  grace-период должен переживать только сворачивание/разворачивание в рамках одного процесса.
- **`PinSetupSheet`** — если PIN уже задан, сначала проверка старого, затем новый вводится
  ДВАЖДЫ (защита от опечатки, которая заперла бы владельца). Длина сознательно гибкая (4-6 цифр) —
  переход «ввод нового» → «подтверждение» **по явному тапу «Продолжить»**, не по достижении
  максимума (иначе PIN был бы принудительно всегда 6 цифр).
- **`PrivacySettingsScreen.kt`** — новая секция «Блокировка приложения»: мастер-тумблер
  (доступен только если задан PIN ИЛИ есть биометрия устройства — `canEnableLock`), строка
  задать/сменить PIN, строка убрать PIN (с предупреждением; если после удаления PIN нет
  биометрии — `appLockEnabled` принудительно выключается, чтобы не запереть владельца).
- **`ContactDetailScreen.kt`** — если биометрии/кода устройства нет, но свой PIN задан,
  `requestReveal()` теперь показывает `PinVerifySheet` вместо немедленного снятия приватности.

### Итоговое правило (сверх §2/§5/§20/§21/§22/§23)

1. Любой `LocalContext.current as? SomeActivityType`/`is SomeActivityType` — по умолчанию считать
   подозрительным в этой кодовой базе (из-за `LocalizedApp`/`createConfigurationContext`), искать
   и переводить на `findActivity()`; при находке ОДНОГО такого места — грепнуть весь репозиторий
   на остальные (`LocalContext.current as?`), не чинить только то место, что было в фокусе задачи.
2. Фича «замочек»/«блокировка» с визуальным индикатором защиты (иконка, блюр, бейдж) — ОСОБЕННО
   рискованна: баг делает её тихо декоративной, но выглядит она как работающая. Логику
   аутентификации в таких местах — трассировать до реального вызова API, не доверять факту, что
   код «выглядит как вызов BiometricPrompt».

### Добавление 2026-07-06 — прямое тестирование владельцем нашло ещё 4 проблемы

Владелец прямым текстом попросил протестировать весь путь от включения приложения до настройки
PIN/биометрии и явно указал два симптома: «шторка не полностью открывается» при вводе PIN и
«чего-то не хватает какой-то валидации и защиты» при добавлении биометрии. Оба подтвердились +
нашёл ещё 2 связанных пробела при разборе логики:

- **`AureliaSheet` (общий компонент ВСЕХ шторок в приложении) не передавал `sheetState` в
  `ModalBottomSheet`** → дефолт `skipPartiallyExpanded = false`. Для высокого контента (PIN-клавиатура
  ощутимо выше типичной формы с текстовыми полями) шторка открывается в состоянии `PartiallyExpanded`
  и обрезает нижние ряды/кнопки — именно «шторка не открывается полностью». Фикс — один параметр
  (`rememberModalBottomSheetState(skipPartiallyExpanded = true)`), чинит СРАЗУ все шторки приложения,
  не только PIN — они просто раньше не были достаточно высокими, чтобы баг стал заметен (тот же
  класс ошибки, что У69 в §23: контрол/компонент, ставший «заметнее» в новом сценарии, вскрывает
  старый скрытый баг).
- **Тумблеры «Защита записей» и «Блокировка приложения» включались МГНОВЕННО, без проверки, что
  аутентификация реально работает.** Ставился персистентный флаг по одному тапу — если биометрия на
  устройстве настроена не до конца или сломана, владелец узнал бы об этом только в момент, когда его
  уже заперло (для app-lock) или заметка перестала бы раскрываться (для «Защищено»). Теперь включение
  ведёт через реальный `BiometricGate.authenticate()`/`PinVerifySheet` — флаг ставится только на
  `onSuccess`.
- **`verifyPin()` не ограничивал число попыток вообще.** 4-6-значный PIN разбирается конечным (и
  небольшим) числом тапов без всякого троттлинга — реальная брешь для короткого PIN. Добавлена
  персистентная (не сбрасывается перезапуском процесса) эскалирующая блокировка: 5 неудач → 30 сек,
  7 → 60 сек, 9+ → 5 мин. Попытки во время самой блокировки не считаются (иначе блокировка
  продлевалась бы бесконечно от продолжения набора).
- **Не было пути восстановления при забытом PIN.** Забытый PIN + недоступная/сломанная биометрия
  раньше означали, что владелец НАВСЕГДА заперт от `AppLockScreen` — а значит и от реальных личных
  данных. Это прямое нарушение правила проекта «потеря данных недопустима» (§0), поскольку
  недоступные данные для владельца эквивалентны потерянным. Проверил: свой PIN НЕ шифрует БД (она
  остаётся открытым SQLite — SQLCipher всё ещё открытый пункт §20), т.е. это чисто программный гейт
  UI, а не настоящее шифрование. Раз так — сброс именно замка (без затрагивания контактов/БД)
  безопасен по сути и необходим по правилу проекта. Добавлена кнопка «Забыли PIN-код?» на
  `AppLockScreen` → `AlertDialog`-подтверждение (тот же паттерн трения, что и «Опасная зона» в
  `PrivacySettingsScreen.kt` — не более и не менее строгий, чем уже принятый в проекте для
  необратимых действий) → `AppSettings.clearPin()` + `appLockEnabled = false` + мгновенный вход,
  данные не трогаются.

**Итог:** качество реализации из первого прохода (§24 выше) было структурно верным (архитектура,
разделение ответственности, шифрование PIN), но **проверка на реальных пользовательских сценариях
(«что если сломается», «что если забуду», «что если контент выше обычного») нашла именно те дыры,
которые статический аудит и компиляция не ловят.** Урок: после любой auth/security-фичи — отдельным
проходом продумать три вопроса (не только «работает ли happy path»): (а) что если способ проверки
не настроен/сломан — есть ли обратная связь ДО того, как включили защиту; (б) что если контент выше
обычного — ведёт ли себя shared-компонент (шторка, диалог) так же корректно, или он тестировался
только на типичном по высоте контенте; (в) что если пользователь сам забыл свой секрет — есть ли
путь назад, не требующий потери данных.

### Реальная потеря данных — «Преобразовать контакт в компанию»

`AppStateStore.convertContactToCompany()` переносил только phones/emails/addresses/notes и

**Решение (сознательно НЕ через миграцию БД):** `Company` не имеет полей под большинство этих
понятий (personalDetails/gifts/sizeInfo и т.п. — личные, не деловые концепты; добавлять их означало
бы клонировать Contact в Company ради разового edge-case экрана). Мигрировали только то, что
переносится БЕЗ схемы: фото → `logoUri` (поле уже существовало, просто не заполнялось) и ссылки
календарных событий (`CalendarItemLink`, targetType CONTACT→COMPANY) — тем же паттерном
ретаргетинга, что уже применяется при слиянии дублей (`mergeContacts`). Всё остальное потерянное —
теперь **честно и полностью** перечислено в `cd_convert_company_text` (все 3 локали), вместо
частичного списка. **Урок:** если функция объективно теряет данные и переносить их некуда — не
изобретать миграцию ради галочки, а сделать предупреждение полным. Молчание о потере — хуже,
чем сама потеря (владелец хотя бы может отказаться).

### WorkTab — дублирующий диалог адреса (СЛОМАНО, не просто «требует полировки»)

Вкладка Работа держала СВОЮ копию диалога адреса с урезанным списком типов (только

### Дисциплина проверки после долгой сессии (важно для будущих сессий)

Прямая обратная связь владельца: «ты обычно допускаешь ошибки, когда долго делаешь» — попросил
проверить уже сделанное, прежде чем продолжать. Обнаружилось: между вызовами инструментов был
разрыв контекста (один фоновый gradle-процесс получил статус `stopped`/interrupted), и часть работы
(таски 66-69) была выполнена, но её результат не был виден в текущем окне разговора напрямую —
только через итоговые уведомления «BUILD SUCCESSFUL». **Это ровно тот сценарий, где нельзя
доверять статусам таск-листа как факту** — статус «completed» описывает намерение, не
верифицированный результат. Проверка `git diff` построчно по каждому изменённому файлу — единственный
надёжный способ убедиться, что длинная пачка правок не разошлась с тем, что реально нужно было
сделать. Именно в ходе этой проверки и нашлась регрессия дефолтного типа адреса выше — она НЕ была
бы поймана, если бы просто поверить логам компиляции/тестов (компилируется и не крашится — не
значит «делает то, что задумано»).

**Итоговое правило (сверх §21/§22/§23/§24):**
1. После пачки правок, сделанных за много вызовов подряд (особенно если было прерывание процесса
   между ними) — не доверять статусам таск-листа, перечитать `git diff` по каждому изменённому
   файлу перед тем как докладывать «готово» или продолжать дальше.
2. Миграция экрана на общий/канонический компонент — ВСЕГДА сверять неявные дефолты компонента
   (не только его сигнатуру) с контекстом конкретного вызывающего места; несовпадение дефолта —
   самый тихий и незаметный класс регрессии, т.к. компилируется и «работает» без ошибок.

### Добавление — SocialShape: консолидация 173 хардкод-вызовов RoundedCornerShape

Прямое решение владельца (после уточнения, что это не баг, а внутренняя не-унификация кода):
«я изначально говорил чтобы не было точечных решений, а общий код который распространяется на
всё, корневой» — довести до конца, не оставлять как техдолг.

`MaterialTheme.shapes` не использовался нигде; вместо единого источника форм по кодовой базе было
рассеяно ~173 хардкод-вызова `RoundedCornerShape(N.dp)` с 18 разными значениями N (3–28dp) в
30 файлах. **Решение — БЕЗ снэппинга близких величин друг к другу**: в `SocialShape`
(`DesignTokens.kt`) добавлены токены под КАЖДОЕ реально использовавшееся значение (`R3`, `R5`,
`R6`, `R7`, `R9`, `R10`, `R11`, `R13`, `R14`, `R15`, `R18`, `R22` — рядом с уже существовавшими
`XSmall`/`Small`/`Medium`/`Large`/`XLarge`/`Full`/`Card`/`Sheet`/`Search`/`Chip`). Это чистая
консолидация источника истины — **визуал нигде не изменился**, просто у каждого угла теперь один
канонический токен вместо разбросанного магического числа. Флагнуто, но НЕ тронуто в этом же
проходе: «радиус шторки» задан в ТРЁХ разных местах с ТРЕМЯ разными значениями (`SocialShape.Sheet`
= 24dp, `AppleDesignSystem.sheet` = 20dp, фактический угол `AureliaSheet` = 28dp) — снэппинг этих
трёх к одному значению уже меняет реальный визуал, требует проверки живьём на устройстве, не
вслепую через `sed`.

**Собственная ошибка в процессе, пойманная при самопроверке ДО сдачи (не после):** первый проход
автозамены (`sed`) слепо матчил `RoundedCornerShape(N.dp)` и заменял его на
`com.aistudio.socialsphere.crmlxb.ui.theme.SocialShape.Token` — но 35 мест из 173 уже писали вызов
ПОЛНОСТЬЮ КВАЛИФИЦИРОВАННЫМ путём (`androidx.compose.foundation.shape.RoundedCornerShape(...)`),
и слепая замена оставляла осиротевший префикс `androidx.compose.foundation.shape.` перед новым FQN
— компилятор ожидаемо не собрался («Unresolved reference 'com'») в 10 файлах. Исправлено точечным
`sed` по самому префиксу, пересобрано и протестировано заново. **Урок:** при массовой текстовой
замене (`sed`/regex) по всей кодовой базе — ПЕРЕД тем как считать это готовым, грепнуть, нет ли уже
существующих fully-qualified вызовов той же функции/класса, которые заменяемый паттерн может
матчить как ПОДСТРОКУ (а не только как самостоятельный, изолированный вызов) — иначе автозамена
сама плодит ровно тот класс тихих регрессий, который декларировано пытается вычистить.

READ-only агента с установкой ИСКАТЬ конкретные баги (не пересказывать диф) по кластерам:
PIN/AppLock, конвертация в компанию + адреса, миграция диалогов на AureliaFormSheet/пикер,
SocialShape + локали. Из ~25 проверенных сценариев подтвердилось 3 реальных бага:

1. **PIN-блокировка держалась на настенных часах.** `pinLockedUntil`/`pinLockRemainingMs()`
   (`SettingsState.kt`) считали от `System.currentTimeMillis()` — перевод даты/времени вперёд в
   системных Настройках снимал анти-брутфорс блокировку PIN мгновенно, без ожидания эскалирующего
   таймаута. Фикс — `android.os.SystemClock.elapsedRealtime()` (монотонные часы с момента загрузки,
   не подвержены смене даты/времени пользователем; сбрасываются только при перезагрузке устройства,
   что само по себе не дыра — просто снимает блокировку раньше срока).
2. **Не было защиты от двойного тапа на кнопке подтверждения `AureliaFormSheet`.** Для форм
   ДОБАВЛЕНИЯ (заметка/подарок/важная дата и т.п.), где `id = UUID.randomUUID()` генерируется
   ВНУТРИ `onConfirm`, быстрый повторный тап до закрытия шторки создавал ДВЕ записи с разными id.
   Баг существовал и ДО перевода этих диалогов на `AureliaFormSheet` (не регрессия миграции — в
   исходных `Button`/`AlertDialog` тоже не было защиты), но раз каркас теперь один канонический —
   фикс (`submitted`-флаг, блокирующий повторный `onConfirm` до пересоздания composable) чинит это
   сразу везде, где используется компонент.
3. **Контакт с пустым именем (только nickname) — невидимая, ненаходимая поиском строка в пикере
   участника события** (`CalendarItemEditScreen.kt`, `AureliaPickerSheet`). `title = "${firstName}
   ${lastName}".trim()` при обоих полях пустых давал `title=""` — пустой кружок аватара без
   инициалов, невидимый текст, и поиск (фильтрует только по `title`/`subtitle`) не находил такой
   контакт вообще ни по чему. Баг существовал и в старом `DropdownMenu` (та же строка), встроенный
   поиск в `AureliaPickerSheet` просто сделал его заметнее. Фикс — фоллбэк на nickname, затем на
   уже существующую в проекте строку `imp_no_name` («Без имени»), по аналогии с готовым паттерном
   в `ContactEditScreen.kt:259`.

**Всё остальное проверенное — чисто**, включая специально проверенные сценарии гонок состояний
(`AppLockState` при повороте/смене языка, ON_STOP/ON_START grace-период, двойной `onUnlocked()` от
биометрии+PIN одновременно — все безопасны/идемпотентны), обход блокировки через `PinSetupSheet`
(троттлится тем же персистентным счётчиком, что и `PinVerifySheet`), поток данных в
`convertContactToCompany()` (порядок операций корректен, ссылки календаря ретаргетятся ДО удаления
контакта), позиционные аргументы `AddressEditDialog` после добавления `defaultType` (везде именованные
— сдвига не произошло), `confirmEnabled`/`onDismiss`-vs-`onSecondary` согласованность во всех
мигрированных диалогах, полнота второго прохода sed по `SocialShape` (0 сросшихся префиксов, 0
забытых одиночных вызовов, синхронность `lock_*`/`cd_convert_company_text` по всем 3 локалям).

**Урок:** второй, адверсарный проход («найди баги», не «перескажи изменения») после уже
проверенной построчным `git diff` работы — вскрыл 3 бага, которые построчное чтение диффа само по
себе не поймало бы (это не ошибки в ЛОГИКЕ диффа — код формально верен, это упущенные ГРАНИЧНЫЕ
случаи: смена системных часов, двойной тап, пустое имя контакта). Построчный дифф ловит «код делает
не то, что написано в комментарии»; адверсарный поиск багов по чек-листу конкретных сценариев
ловит «код делает то, что написано, но написанное не покрывает все входы». Оба прохода нужны для
разных классов ошибок, один не заменяет другой.

### Добавление — реальный баг на живом устройстве, пропущенный ВСЕМИ предыдущими проверками

Владелец протестировал вживую и сообщил: тумблер «Защита записей» и замочек в карточке контакта —
не делают вообще ничего (ни запроса биометрии, ни PIN), при включении «Блокировки приложения»
экран установки PIN появляется, но выглядит криво и «не дружит с клавиатурой», а биометрия не
запрашивается ни при запуске, ни при защите.

**Корневая причина — одна, реальная, найдена и почина:** тумблер «Защита записей»
(`PrivacySettingsScreen.kt`, `biometricLock`) имел `enabled = bioAvailable` — ТОЛЬКО проверку
наличия биометрии на устройстве, полностью игнорируя `hasPin`. На любом устройстве без биометрии
(нет отпечатка/лица в системных Настройках) тумблер был НАВСЕГДА неактивен — тап по нему не делал
ничего, вообще без исключений, ровно как владелец и описал. Это, в свою очередь, объясняет и
замочек в карточке контакта: `requestReveal()` начинается с `!bioLockOn -> privacyMode = false` —
если `bioLockOn` в принципе никогда не мог стать `true` (тумблер не включался), эта ветка
срабатывает всегда и молча снимает приватность без единого запроса аутентификации — то самое
«ничего не происходит». Тумблер «Блокировка приложения» (`appLockEnabled`) был исправен с самого
начала (`enabled = canEnableLock = hasPin || bioAvailable`) — поэтому PIN там ВКЛЮЧИТЬСЯ смог, но
делал это через отдельный, отдельно найденный визуальный баг:

- **Кнопка «Продолжить» в установке PIN** — единственный элемент всего PIN-флоу на голых
  Material3-дефолтах (маленькая пилюля произвольной ширины) вместо стиля всего остального проекта
  (широкая акцент-кнопка 48dp/`SocialShape.R14`, как в `AureliaFormSheet`) — то самое «коряво».
- **Высота содержимого почти упиралась в потолок шторки** — `PinEntryBody` с полным набором
  элементов (заголовок+точки+клавиатура+кнопка «Продолжить») давала ~560dp контента ровно на
  границе `AureliaSheet`'s `heightIn(max=560.dp)`, а с учётом внутренних отступов шторки —
  превышала его, вынуждая скроллить, чтобы увидеть кнопку/нижний ряд клавиатуры («не дружит с
  клавиатурой» — не про системный IME, про саму цифровую клавиатуру PIN). Отступы уменьшены.

Все три фикса: (1) `enabled = canEnableLock` + `onCheckedChange` по тому же паттерну
«биометрия/иначе PIN», что и у `appLockEnabled`, для тумблера `biometricLock`; (2) стилизация
кнопки «Продолжить»; (3) уменьшение вертикальных отступов `PinEntryBody`.

**Это САМОЕ важное — почему это не поймалось раньше, несмотря на §24/§25 и глубокий адверсарный
аудит:** вся верификация этой сессии — компиляция + JVM unit-тесты (Robolectric) + статическое
чтение кода/`git diff` + 15 параллельных READ-only агентов. **Ни разу за всю сессию приложение не
запускалось на реальном устройстве/эмуляторе.** Unit-тесты не рендерят реальный Compose UI, не
проверяют реальное поведение `Switch.enabled`, не проверяют, показывается ли `BiometricPrompt`
физически, не проверяют реальные инсеты IME/клавиатуры. «Компилируется и тесты зелёные» — необходимое,
но НЕ достаточное условие корректности Android UI. Баг с `enabled = bioAvailable` формально
компилировался идеально и не имел никакой логической ошибки В КОДЕ ГДЕ ОН НАПИСАН — ошибка была в
том, что соседний, уже написанный код (`hasPin`-фоллбэк в `requestReveal()`) подразумевал, что
включить защиту можно и без биометрии, а тумблер ЭТОГО НЕ ПОЗВОЛЯЛ — рассинхрон между двумя
частями фичи, который не ловится ни компилятором, ни unit-тестом, ни чтением одного файла — только
реальным тапом по реальному экрану.

**Итоговое правило (сверх всех предыдущих §):** для Android/Compose UI-фич — «собралось + тесты
прошли» НИКОГДА не значит «работает при тапе». Если нет доступа к реальному устройству/эмулятору
для верификации, это ограничение нужно явно проговаривать владельцу СРАЗУ, а не после того как он
сам найдёт баг вживую. Особенно рискованная зона — множественные точки входа в одну логическую фичу
(тумблер настроек + иконка в другом экране + PIN vs биометрия как альтернативные пути) — при правке
одной точки входа обязательно грепать и сверять ВСЕ остальные точки входа той же фичи на тот же
паттерн условия/gating, а не полагаться на то, что раз одна точка исправлена — исправлены все.

несколькими точками входа на один флаг (тумблер настроек + иконка на другом экране + PIN/биометрия
как альтернативные способы) — это и есть системная причина, не разовая опечатка.

## 26. КРИТИЧНО — найдена и устранена настоящая причина «теряю данные при каждом обновлении» (2026-07-07)

**Это, вероятно, самый серьёзный баг всей сессии** — прямая причина многократных жалоб владельца
на потерю заметок/дат/других полей при каждом обновлении приложения.

**Корень:** в `SocialsphereDatabase.kt`, функция `getDatabase()`, стоял
`fallbackToDestructiveMigration()`, включённый условием `if (BuildConfig.DEBUG)`. Владелец
пользуется именно debug-сборкой (отдельного release-конвейера нет) — то есть это условие было
активно ВСЕГДА на его телефоне. Room выбирает этот путь, когда не может подтвердить точное
совпадение схемы (identity hash) — а такое рассогласование возникает практически при КАЖДОЙ правке
`@Entity` (что в этом проекте происходит постоянно, почти на каждой сессии). При срабатывании
Room молча **дропает и создаёт заново все таблицы** — без исключения, без предупреждения, без
диалога. Итог для владельца: контакты/заметки/даты просто пустые при следующем запуске после
обновления apk — ровно то, что он описывал.

**Важно:** сами миграции (`MIGRATION_1_2` … `MIGRATION_12_13`, версии 1→13) были все на месте, без
пропусков, и в целом верны — проблема была не в них, а в том, что destructive-fallback их вообще
обходил при любом малейшем расхождении.

**Фикс:**
- Убран `fallbackToDestructiveMigration()` целиком и неиспользуемый импорт `BuildConfig` из
  `SocialsphereDatabase.kt`. Теперь при отсутствии валидного пути миграции Room **упадёт с громким
  исключением** (описывающим конкретное несовпадение схемы) — это заметно и чинится разработчиком,
  а не тихо стирает боевые данные владельца.
- Добавлен новый постоянный тест-страховка в `MigrationTest.kt`:
  `fullMigrationChain_6to13_preservesContactData_noExceptions` — прогоняет ВСЮ цепочку миграций
  6→13 подряд на одной реальной in-memory SQLite (Robolectric), начиная с ПОДЛИННОЙ схемы v6 (взята
  дословно из экспортированного `app/schemas/.../6.json`, не придумана), и проверяет: (а) ни одна
  миграция не бросает исключение, (б) вставленная строка контакта доживает до v13 со всеми
  исходными полями нетронутыми, включая появление новых колонок как `NULL` (не потеря данных).
  Если когда-нибудь в будущем добавят миграцию с пропуском версии или опечаткой в SQL — этот тест
  упадёт в CI/локальной сборке раньше, чем баг доберётся до устройства владельца.
- Проверено: `compileDebugKotlin testDebugUnitTest` — `BUILD SUCCESSFUL` дважды подряд (сначала без
  нового теста — подтверждает, что сам фикс не ломает ничего существующего; затем с новым тестом
  включённым — подтверждает, что вся цепочка миграций реально работает без destructive fallback).
  `qa_check.py` — зелёный.

**Урок на будущее:** «защитный» `fallbackToDestructiveMigration()` для debug — частый шаблон в
туториалах Android, но он **опасен по умолчанию** в любом проекте, где debug-сборка — это боевое
приложение реального человека, а не только среда разработки. Если такой fallback когда-либо
понадобится вернуть (например, ради удобства при активной разработке), он ДОЛЖЕН быть за явным
доп.-флагом, отдельным от `BuildConfig.DEBUG`, и никогда не должен включаться в сборке, которую
устанавливает владелец на свой телефон. Полное покрытие миграциями без пропусков делает fallback
попросту ненужным.

## 27. Живая верификация фикса потери данных + весь оставшийся чек-лист (2026-07-07)

По прямому требованию владельца («прогони все записи новые тесты раз у тебя есть доступ к эмуляции
прогони весь список») — не unit-тесты, а реальный эмулятор, каждый пункт вживую:

1. **Главный тест самого фикса (§26).** На реальном installed APK испорчен `identity_hash` в
   `room_master_table` (ровно то рассогласование схемы, что раньше включало destructive fallback).
   Перезапуск → Room бросил `IllegalStateException: Room cannot verify the data integrity... Expected
   identity hash: ..., found: deadbeef...` — **громкий крэш**, не тихий снос. Проверено `sqlite3` через
   `run-as`: все 5 тестовых контактов остались в БД целыми. Восстановлен верный hash → приложение снова
   открылось нормально, данные на месте. Это прямое, а не косвенное доказательство: раньше именно это
   рассогласование стирало данные владельца молча, теперь — падает заметно и без потерь.
2. **«Забыли PIN-код»** (§61) — диалог честно предупреждает "Контакты, компании и остальные данные это
   НЕ затронет", после сброса `app_pin_hash`/`app_lock_enabled` очищены, все контакты подтверждены целыми.
3. **Валидация включения блокировки** (§59) — переключатель «Блокировать приложение» при включении
   требует подтверждения существующим PIN («Подтвердите разблокировку, чтобы включить защиту») — вживую
   подтверждено, не только по коду.
4. **Лимит попыток подбора PIN + эскалация блокировки** (§60) — 5 неверных попыток подряд → живой текст
   «Слишком много попыток. Попробуйте через 30 сек.» — подтверждён точный порог (4 бесплатных, 5-я
   ловит блокировку) и `pinLockedUntil` через `SystemClock.elapsedRealtime()` (не wall-clock).
5. **Grace-период 30 сек** (`MainActivity.kt`, `APP_LOCK_GRACE_MS`) — свернул приложение на ~2 сек →
   разворот БЕЗ повторного PIN. Свернул на >30 сек → разворот С запросом PIN. Оба сценария подтверждены
   вживую впервые в этой сессии.
6. **Конвертация контакта в компанию** (§65) — диалог подтверждения честно и подробно перечисляет, что
   именно перейдёт (телефоны/email/адреса/заметки/фото/события), а что будет потеряно безвозвратно
   (мессенджеры/подарки/личные детали/размеры/теги/семья/профессия/группы) — и что карточка контакта
   будет удалена. Подтверждено вживую: после «Преобразовать» контакт корректно стал компанией с полным
   набором вкладок (Люди/Контакты/Адреса), без крэша.

**Побочная находка процесса (не баг фичи, снова урок по методике тестирования):** при вводе
PIN на двух РАЗНЫХ экранах (создание нового / подтверждение нового) вертикальные координаты клавиатуры
слегка отличаются даже в рамках одной and той же шторки (заголовок другой высоты/обёртки), и ещё раз
сдвигаются при появлении текста ошибки под заголовком. Дважды промахнулся мимо кнопки «Продолжить» и
дважды — мимо цифр, потому что переиспользовал координаты с предыдущего шага вместо свежего
`uiautomator dump` перед КАЖДЫМ отдельным тапом. Также: `run-as ... sqlite3 ... "SELECT count(*)..."`
через `adb shell` требует обёртывать всю удалённую команду в одинарные кавычки (`adb shell "run-as ...
'SELECT ...'"`), иначе локальный shell разбивает скобки `count(*)` как синтаксис.

**Итог:** ни один из проверенных вживую пунктов не оказался багом приложения — все расхождения при
тестировании были следствием неточных координат/гонки чтения `SharedPreferences.apply()` с моей стороны,
не логики кода. Все механизмы (лимит попыток, grace-период, честные предупреждения о потере данных,
восстановление PIN, и главное — устранение silent data loss) подтверждены работающими на реальном
эмуляторе, не только по исходному коду.

## 29. Работа над ошибками — архитектура безопасности контактов (2026-07-08/09)

Владелец прямо указал: система защиты (PIN/биометрия/приватность записей) спроектирована
поверхностно — «слишком мало пунктов в безопасности», решения принимались хардкодом вместо
архитектуры, одно и то же чинится по десять раз. Полный разбор ниже — что было не так, что
исправлено, и какое правило теперь действует на будущее.

### Найденные и исправленные баги

**1. Биометрия не включалась.** `BiometricGate.isAvailable()` делал ОДИН вызов
`canAuthenticate(BIOMETRIC_WEAK or DEVICE_CREDENTIAL)`. Подтверждено экспериментально: на
эмуляторе с реально настроенным системным кодом блокировки (`locksettings set-pin`, проверено
`get-disabled: false`, экран блокировки реально появлялся) `BiometricService` в логах вернул
`Status: 7` (не успех) **и для комбинации, и для каждой модальности по отдельности** — платформенная
хрупкость именно комбинированного вызова. **Фикс:** `BiometricGate.kt` теперь проверяет
`BIOMETRIC_WEAK` и `DEVICE_CREDENTIAL` РАЗДЕЛЬНО и берёт тот набор, который реально доступен —
один нерабочий комбо-вызов платформы больше не блокирует переключатель целиком.

**2. Точки PIN всегда 6, независимо от реальной длины.** `AppLockComponents.kt`: `PIN_LENGTH = 6`
был единственной длиной, которую УМЕЛИ показывать экраны разблокировки — а `AppSettings.setPin()`
сохранял только соль+хеш, длину нигде не хранил, поэтому UI физически не мог знать, сколько точек
рисовать. **Фикс:** добавлено персистентное `AppSettings.currentPinLength()` (сохраняется в
`setPin()`, сбрасывается в `clearPin()`); `AppLockScreen`/`PinVerifySheet` используют его как
`maxLength`, проверка PIN — строго на этой длине, а не на диапазоне 4-6.

**3. Замочек приватности в карточке контакта был виден всегда.** `ContactDetailScreen.kt`:
кнопка в шапке рисовалась безусловно, даже если «Защита записей» вообще выключена в Настройках —
тап всё равно «включал» приватность на сессию, что не имело смысла. **Фикс:** кнопка обёрнута в
`if (bioLockOn)`.

### Архитектурная переделка — приватность заметки

Было: `isImportant` — одно поле на три несвязанных смысла (красная рамка + попадание в Обзор/
Шпаргалку + скрытие блюром под приватностью). Заметка «важная, но не секретная» пряталась;
реально приватная без галочки важности — не пряталась. Владелец сам это вскрыл вопросом
«какая-то галочка есть, что скрывать?».

**Решение — не хардкод категорий, а изучение того, как это уже решено лучшими:**
- iOS Notes: пароль на заметки — предварительное условие, но какие ИМЕННО заметки скрыть,
  владелец решает вручную по одной, отдельным действием. По умолчанию не скрыто ничего.
- WhatsApp Chat Lock: та же архитектура — вручную выбранный чат уходит в отдельную папку под
  биометрией/кодом, не автоматическая категория переписок.

Оба самых отточенных на рынке решения сходятся в одном: **явный выбор по каждой записи**, не
автоматика по типу/вкладке. Реализовано:
- Новое поле `Note.isLocked` (миграция v13→14, `MIGRATION_13_14`, `notes.isLocked INTEGER NOT
  NULL DEFAULT 0`) — независимо от `isImportant`.
- `isImportant` остаётся только «попадает в Обзор/Шпаргалку + красная рамка».
- `isLocked` — отдельная галочка «Скрыть при блокировке» в диалогах добавления/правки заметки
  (видна только если «Защита записей» включена — как в iOS, где сначала нужен пароль) + пункт
  «Скрыть/Не скрывать» в меню записи (⋮).
- `NotesTab.kt`: `protectedHidden = privacyMode && note.isLocked` (было: `&& note.isImportant`).
- Тест `migration13to14_addsIsLocked_defaultsFalse_keepsExistingNotes` на подлинной схеме notes
  из `13.json` — старые заметки не помечаются приватными задним числом.

### Правило на будущее — исследовать, не хардкодить

Владелец отдельно указал на паттерн: я предлагаю решение «из головы» (хардкожу категории/поля),
хотя для большинства UX/архитектурных вопросов уже есть проверенное индустрией решение —
нужно **сначала искать** (WebSearch/документация конкретных систем: iOS/Android/WhatsApp/AOSP),
потом проектировать, а не наоборот. Это же применимо к системным вопросам самого приложения —
например, `ContactsScreen.kt:368` жёстко сортирует по `firstName` прямо в Composable вместо
конфигурируемого `ContactDisplayPreferences` (sortBy/nameFormat), хотя в Android Contacts это
két отдельные, давно устоявшиеся настройки (см. §30 при заведении).

**Правило верификации на реальном устройстве, подтверждённое повторно:** при отладке
эмулятора (PIN на системном экране блокировки не вводился) я слишком долго перебирал `input
swipe` вместо того, чтобы сразу перейти на `wm dismiss-keyguard` (сработал с первого раза
раньше в этой же сессии) — при столкновении с сопротивлением среды пробовать 2-3 разных
метода параллельно, а не долбить один и тот же безуспешно.

### Живая верификация всех трёх фиксов на эмуляторе (2026-07-09) — ПРОЙДЕНА

По требованию владельца («проверяй заново, я не вижу позитивных изменений») все фиксы §29
проверены глазами на эмуляторе, свежая сборка:

1. **Точки PIN по факту длины** — задан 4-значный PIN: экран блокировки приложения,
   PinVerifySheet и шторка «Показать защищённые записи» показывают ровно 4 точки (не 6);
   разблокировка срабатывает автоматически на 4-й цифре.
2. **Биометрия включается** — с системным кодом устройства (locksettings set-pin) подпись
   переключателя сменилась на «Отпечаток или код устройства…», переключатель включился
   через подтверждение PIN (checked=true). Это и был сценарий «биометрия не включается»:

## 32. Полный аудит локализации (2026-07-11) — реальные баги, не там, где подозревали

Владелец подозревал: (а) не всё переводится, (б) что-то требует перезапуска, (в) новые

**Исследование API (WebSearch, не по памяти):** сравнил текущий ручной
`createConfigurationContext` (`LocalizedApp` в `SettingsState.kt`) с официальным
`AppCompatDelegate.setApplicationLocales()`/`LocaleManager` (Android 13+). Решение —
**не мигрировать**: официальный путь требует добавить `androidx.appcompat` (сейчас его
нет в зависимостях), надёжная реализация не должна ограничиваться только бэкпортом
(нужен ручной dual-path LocaleManager на API 33+, иначе OEM-сборки теряют выбор после
смерти процесса), и означает `Activity.recreate()` при смене языка вместо мгновенного
`CompositionLocalProvider` — а у текущего подхода не осталось непосредственных багов
(единственный класс багов от него — Context-ловушки при `as? Activity` — уже поймали и
пофиксили `findActivity()`-обходом в прошлых сессиях, повторный аудит `as? Activity`
по всей кодовой базе новых мест не нашёл).

**Android Lint `HardcodedText` — тупик для Compose.** Включил (`app/build.gradle.kts`,
`lint { error += "HardcodedText" }`), прогнал `lintDebug` — 0 совпадений. Причина: этот
чек ловит только XML `android:text="..."`, а проект на 100% Compose — `Text("...")` в
Kotlin вне его области видимости. Оставил чек включённым (не мешает, ловит будущие XML,
если появятся), но реальный барьер — регэксп-сканер в `qa_check.py` (У49).

**У49 был allowlist — именно поэтому новые экраны не проверялись.** Список файлов

попадает под проверку кириллицы (У49, denylist) без ручного добавления в список.
Живая проверка на эмуляторе всех 3 языков — обязательна перед тем, как считать фичу
локализованной, статический анализ такие вещи как #3 и #4 (списки ролей, ширина
колонки) не ловит в принципе.

## 33. Мультиагентный workflow-план + критик поймал две реальные ошибки (2026-07-11)

Впервые опробован сохранённый workflow `.claude/workflows/socialsphere-plan-feature.js` (research +
codebase-impact + design-fit параллельно → synthesis → critique) на задаче «сканер визиток даёт
билиберду». Диагноз всех отчётов сошёлся: не движок Tesseract виноват, а конфигурация — не задан
`PageSegMode` (дефолт PSM 3 «авто-сегментация страницы» — худший выбор для разреженного текста
визитки, нужен PSM_SPARSE_TEXT), плюс рамка-гид `ScanFrameOverlay` в `CardCameraScanner.kt` была
декоративной — в OCR уходил весь необрезанный кадр со столом/фоном.

**Критик (5-й агент, добавлен по фидбэку владельца «ты иногда ленишься») нашёл то, что план
проглядел:**
1. **CONFIRMED** — план не проверил реальную сигнатуру `TessBaseAPI` API, написал «в зависимости от
   версии библиотеки» вместо того чтобы открыть исходник.
2. **CONFIRMED** — кроп по рамке-гиду не учитывал, что координаты Compose-превью (dp, экран) и
   пиксели захваченного bitmap (разрешение сенсора камеры) — РАЗНЫЕ системы координат; наивный кроп
   резал бы не ту область в большинстве случаев.

**При устранении #1 сам чуть не наступил на ту же грабли:** первая «проверка» через WebFetch (сжатие
исходника маленькой моделью) ошибочно сообщила, что `PSM_SPARSE_TEXT` — прямая константа
`TessBaseAPI`. Реальность (перепроверено вторым точечным запросом с явной просьбой процитировать
код): `PSM_SPARSE_TEXT` лежит во вложенном `TessBaseAPI.PageSegMode`, а `OEM_LSTM_ONLY` — на самом
`TessBaseAPI`. Сборка сразу поймала это (`Unresolved reference`) — компилятор как последний рубеж
проверки, даже когда «проверка через источник» уже была сделана и тоже ошиблась.

**Фикс `#2` (несовпадение координат)** решён не ручным пересчётом масштаба, а штатным механизмом
CameraX — общий `ViewPort` между `Preview` и `ImageCapture` через `UseCaseGroup` (WYSIWYG: что видно
в превью, то и попадает в снимок), дробная геометрия рамки (`cardFrameRect()`) вынесена в общую
функцию для отрисовки и кропа — раньше были две независимые копии.

**Живая проверка — с честной оговоркой.** У эмулятора нет реальной камеры (синтетический тестовый
узор вместо кадра), поэтому подтверждено только: путь съёмка→кроп→OCR→парсер не крашится, новый
Tesseract API (`init(dataPath, LANGS, OEM_LSTM_ONLY)` + `pageSegMode = PageSegMode.PSM_SPARSE_TEXT`)
реально инициализируется и выполняется (`libtesseract.so` загружен, экран корректно возвращается к
состоянию проверки текста). **Не проверено и не может быть проверено в этом окружении:** стала ли
билиберда на настоящей визитке реально меньше — это требует физического устройства с камерой и
реальных карточек владельца.

## 34. Статусы/карточка контакта, дубли компаний, адреса — разбор причин + баги + дисциплина проверки (2026-07-23/27)

Владелец голосовым сообщением разобрал карточку контакта целиком («статусов слишком много и
непонятно», «на карточке ты слишком много выставляешь, а обзор сужаешь») и отдельно попросил
паритет компаний с контактами (поиск дублей). Позже, после живой проверки первого раунда правок,
дал ВТОРОЙ голосовой разбор с прямыми претензиями к тому, что сам же недодумал в реализации —
«что ещё за ограничения, как ты собираешься ставить [Custom]», «форма компании — исправь», «демо-
данные удали и больше никогда не ставь», «предложи решение [про snackbar], а не просто опиши
проблему». В конце сам же спросил, почему на одной задаче съедаются все токены — ниже прямой
разбор и этой части тоже, без сглаживания.

### Почему владелец попросил каждую правку (не просто список изменений)

- **Множественный статус (тип отношений)** — «твой коллега может быть и другом одновременно»:
  одно поле `relationshipType` не могло выразить два одновременно верных факта о человеке.
- **Убрать теги/next-step/дату из шапки карточки** — «зачем дублировать в карточке, когда сразу
  видишь и карточку, и обзор» — те же данные уже есть на вкладке Обзор, дублирование СУЖАЕТ
  полезное пространство экрана без выгоды.
- **Убрать ImportanceLevel** — прямая цитата из давнего фидбэка самого владельца («статусы не
  очень красивые, яркие, непонятные», см. §11 2026-07-02) — три уровня важности как отдельные
  цветные чипы были визуальным шумом без ясной семантики.
- **Ободок аватара по `contactStatus`, а не важности** — «нужно поддерживать» как самое ценное
  из всех статусов заслуживает визуального акцента вместо словесного чипа.
- **Ритм общения «вручную»** — фиксированные пресеты (неделя/месяц/3 мес/6 мес/год) не покрывают
  реальные интервалы («раз в 45 дней»), `CommunicationRhythm.CUSTOM` уже существовал в enum, но
  был исключён из ВСЕХ пикеров — по факту функция существовала в данных, но была недостижима
  из UI (тот же класс, что «декоративный контрол» из §2, только наоборот — поле без интерфейса).
- **Дубли компаний** — «переняли уже нашу технику с контактов на компании»: у контактов
  инструмент поиска+слияния дублей существовал, у компаний — нет, при том что тот же сценарий
  («визитка/импорт создали вторую запись той же компании») там тоже возможен.

### Найденные баги (не пожелания дизайна — реальные расхождения кода и данных)

1. **CompanyEditScreen — скрытый дубль адреса** (см. также обновлённая запись в §12). Форма
   держала 4 фиксированных именованных поля (офис/филиал/юр.адрес/другое), `upsertAddress` искал
   `list.indexOfFirst { it.addressType == type }` — по одному слоту на `AddressType`. Реальная
   модель этого не ограничивает: у слитой (через `mergeCompanies`) компании оказалось 2 адреса
   типа `OFFICE` — форма показывала и позволяла редактировать только первый найденный, второй
   существовал в БД, но был физически недостижим из UI. Классический баг «поле есть, интерфейса
   для него по факту нет» — тот же класс, что §11 «пропала функция связей» и §21 п.1
   (обнаруживаемость), только источник не гейт `if(editing)`, а структурное ограничение формы
   (один слот вместо списка).
   **Фикс:** секция адресов компании переведена на тот же динамический список + общий
   `AddressEditDialog` (`AddressComponents.kt`), что уже используется у контактов — устраняет
   и сам баг, и дублирование кода (два независимых UI для одной механики — см. У63 §5).
2. **Ритм `CUSTOM` недостижим из быстрого чипа в шапке карточки** — чип `EditableChip` устроен
   как мгновенный дропдаун (тап на вариант → сразу пишется в БД), для `CUSTOM` физически негде
   было ввести число дней, поэтому его вообще исключили из списка вариантов чипа — значение
   можно было поставить ТОЛЬКО через полную форму редактирования контакта, при том что остальные
   5 пресетов ритма были доступны в одно касание из карточки. Обнаружено ретроспективно самим
   владельцем при первой проверке результата: «что ещё за ограничения». **Фикс:** выбор `CUSTOM`
   из чипа открывает мини-шторку ввода числа дней; сам чип отображает «Custom · every N d», не
   просто «Custom» — обнаруживаемость значения, не только доступность выбора.
3. **`officeAddressId` — поле схемы БД, никогда не имевшее интерфейса.** Колонка существовала в
   `ContactCompanyRelation` заметно раньше этой сессии (видна во всех промежуточных схемах),
   но не читалась и не писалась НИГДЕ в UI — типичный «мёртвый задел на будущее», который легко
   потерять из виду и забыть довести до конца. Использован в этой сессии как раз по назначению:
   контакт помечает свой рабочий адрес флажком «это адрес компании X» → `AppStateStore
   .linkContactAddressToCompany()` ищет среди адресов компании совпадение по нормализованной
   улице+городу (та же логика нормализации, что уже используется в дедупе `findCompanyDuplicatePairs`)
   и либо переиспользует найденный адрес, либо заводит один новый — без дублирования данных.
4. **Snackbar Undo слияния — `SnackbarDuration.Short` (~4 сек) для действия, переносящего данные
   нескольких карточек в одну.** Не баг в смысле «не работает», а несоразмерность окна реакции
   риску действия — я сам столкнулся с этим при собственной живой проверке слияния компаний (не
   успел прочитать результат и отреагировать за 4 секунды). Владелец прямо потребовал не просто
   зафиксировать проблему, а предложить конкретное решение с обоснованием (не «просто длиннее», а
   по индустриальному паттерну) — приведена практика Gmail/Google Photos для undo-после-merge/
   delete, применён `SnackbarDuration.Long` в обоих местах (контакты и компании) для единообразия.
5. **Демоданные сеялись при КАЖДОЙ новой установке без возможности отказаться.** Не баг логики,
   прямое продуктовое требование владельца («удали и никогда больше не ставь») — сидинг убран из
   `AppStateStore.loadInitialData()`, сам `DemoDataProvider.kt` удалён целиком (не просто
   отключён вызов — чтобы не осталось соблазна включить обратно точечной правкой).

### Продуктовые/архитектурные решения (не баги — осознанный выбор)

- `ImportanceLevel` убран из UI везде (шапка/форма/фильтры/`CompanyDetailScreen`/`OverviewTab`),
  колонка БД **не удалена** — тот же прецедент, что уже применялся для `ConnectionLevel` (§7 —
  колонка остаётся, просто нигде не читается/не пишется из UI, миграция не нужна).
- `secondaryRelationshipTypes: List<RelationshipType>` — ДОБАВЛЕНО новое поле, существующее
  `relationshipType` НЕ переименовано/не превращено в список — минимизирует блast radius: все
  ~17 старых мест использования `contact.relationshipType` продолжают работать без изменений,
  правки нужны только там, где реально нужна новая логика (форма, шапка, фильтр, поиск, слияние).
- Слияние компаний (`CompanyMerge.kt`, `mergeCompanies`/`undoMergeCompanies`) — построено ТОЧНОЙ
  зеркальной копией уже проверенной архитектуры слияния контактов (транзакция, union+дедуп
  списочных полей, дедуп сотрудников по паре `(contactId, position)` — не по одному `companyId`,
  чтобы вторая должность того же человека на другой позиции не терялась целиком, ретаргет заметок/
  календаря, `Undo`-снапшот) — переиспользование проверенного паттерна вместо изобретения нового.

### Дисциплина проверки на эмуляторе — что снова пошло не так, несмотря на записанные уроки §27/§31

Это САМАЯ дорогая по токенам часть сессии, и владелец прямо спросил, почему. Разбор по фактам:

- **Пиксельный масштаб скриншота (900×2000 показ vs 1080×2400 реал, ×1.2) путал координаты
  повторно** — тот же класс промаха, что уже описан в §27/§31 как «взял координаты не из свежего
  состояния». Отличие в этот раз: не устаревшие координаты между шагами, а систематическая ошибка
  пересчёта масштаба на каждом первом тапе в новой серии действий.
- **`adb shell input swipe` рядом с нижней границей экрана (y>~1900 из 1920 доступных) триггерил
  СИСТЕМНЫЙ жест Android «домой»**, а не скролл внутри приложения — полная потеря контекста формы,
  пришлось перезаходить и вводить данные заново. Раньше в базе знаний такого класса промаха не
  было — новый урок, не повтор.
- **`KEYCODE_BACK` вёл себя непредсказуемо в зависимости от того, ЧТО было активно**: иногда
  закрывал только клавиатуру, иногда — весь `ModalBottomSheet` целиком вместе с несохранённым
  вводом (диалог адреса заполнялся заново дважды из-за этого), иногда — всю форму «Новый контакт»
  с полным сбросом черновика. **Правило на будущее: для закрытия ТОЛЬКО клавиатуры — тап по
  собственной кнопке сворачивания клавиатуры (chevron) или по нейтральному незанятому месту
  экрана, никогда `KEYCODE_BACK`, если контекст (диалог/шторка/форма) не гарантированно переживёт
  это действие.**
- **Эмулятор падал на уровне QEMU/GPU-драйвера хоста (`bad color buffer handle`, hanging thread)
  несколько раз подряд, не связано с кодом приложения.** После одного из падений и холодного
  перезапуска на экране оказались старые демо-контакты («Jane Cooper», «Ivan Petrov», «Anna
  Miller») из давно устаревшего снапшота AVD — совершенно не то, что ожидалось после моего же
  фикса «демоданные больше не сеются». Важно: это НЕ регрессия фикса (подтверждено повторным
  чистым `uninstall`+`install`, показавшим честный пустой старт) — а артефакт состояния конкретной
  машины/снапшота эмулятора, который мог бы ввести в заблуждение, если бы не был перепроверен
  чистой переустановкой перед тем, как делать вывод.
- **Итог по стоимости:** финальная проверка одного узкого сценария (дедуп адреса при повторном
  сохранении контакта с чекбоксом «это адрес компании») заняла заметно больше действий, чем сама
  разработка фичи, — не из-за сложности сценария, а из-за перечисленных выше срывов среды. Логика
  самого фикса была независимо подтверждена построчным чтением кода ДО начала живой проверки —
  что и было явно предложено владельцу как обоснованная точка остановки, когда среда стала
  систематически мешать, а не тихое умолчание о непроверенном.

**Итоговое правило (сверх §21/§27/§31):**
1. Свайпы в пределах ~150-200px от нижней границы экрана — не использовать для внутриэкранного
   скролла на этом эмуляторе (Android gesture-nav перехватывает как системный жест); держать
   свайпы в средней трети экрана.
2. `KEYCODE_BACK` — не универсальный «закрыть верхний слой»; для закрытия именно клавиатуры без
   риска для содержимого — chevron клавиатуры или тап по нейтральной некликабельной области формы.
3. После краха/перезапуска эмулятора — не доверять первому увиденному состоянию приложения как
   отражению текущего кода; при малейшем подозрении (неожиданные данные на экране) — чистая
   переустановка `uninstall`+`install` как источник истины, прежде чем делать вывод о регрессии.
4. Когда живая UI-верификация на конкретной машине систематически ломается по причинам среды
   (не логики) — после разумного числа попыток явно предложить владельцу остановиться на
   подтверждении по коду, а не продолжать жечь токены на борьбу со средой молча.

## 35. Полный аудит «кнопка обещает / кнопка делает» — 6 параллельных агентов, 6 подтверждённых багов (2026-07-27)

Владелец попросил буквально: «проверь в приложении каждую кнопку что она должна делать и что
она делает на самом деле, проверь каждую логику каждую связь». Формулировка означает не «найди
визуальные баги», а конкретно несоответствия между тем, что действие ОБЕЩАЕТ (текст кнопки,
подпись, иконка), и тем, что код реально выполняет — включая тихие потери данных и мёртвые связи
между экранами.

### Почему аудит запускался как 6 параллельных read-only агентов, а не вручную
Ручная UI-проверка на этом эмуляторе — самая дорогая по токенам активность в проекте (см. §34).
Вместо повторного прогона через живой эмулятор каждой кнопки приложения, аудит выполнен статически:
6 `general-purpose` агентов, каждый — своя функциональная зона (Календарь/Карта, Компании, Контакты,
Настройки/Безопасность, вкладки карточки контакта, граф навигации+core-data), каждому — чеклист
известных по этой же базе знаний паттернов багов (обрезание при пересборке сущности, забытые
каскады при удалении, несинхронизированные диалоги, «глухие» обработчики). 4 из 6 агентов упали
с ошибкой лимита сессии аккаунта («session limit · resets 11:20am Europe/Athens») — это внешнее
ограничение API, не брак промпта; эти 4 зоны (Контакты, Настройки/Безопасность, вкладки карточки,
навигация/core-data) остались неаудированными и требуют повторного запуска отдельно.

### Найденные и исправленные баги (все 6, из 2 завершившихся агентов)
1. **[КРИТИЧНО] «Перенести» событие ставило `status = POSTPONED`** (`CalendarItemDetailScreen.kt`,
   постпон-диалог) — а ВСЕ списочные экраны (`CalendarScreen`, `HomeScreen`, `CheatSheetScreen`,
   `CompanyDetailScreen`, `OverviewTab`) фильтруют строго `status == ACTIVE`. Перенесённое событие
   не удалялось и не отменялось — оно просто исчезало из глаз пользователя навсегда, оставаясь
   в БД. `POSTPONED` как статус нигде не читался ни одним UI-фильтром — мёртвая ветка с момента
   создания. Фикс: перенос даты больше не трогает `status` вообще.
2. **Удаление/завершение календарного события не отменяло уже поставленный будильник**
   (`AppStateStore.deleteCalendarItem`/`markCalendarItemCompleted`) — `NotificationScheduler`
   ничего не знает о жизненном цикле события в БД, будильники в `AlarmManager` живут отдельно от
   Room. Фикс — на уровне UI (там, где есть `Context`): оба места вызывают
   `cancelAllRemindersForCalendarItem` перед мутацией стора.
3. **`NotificationScheduler.rescheduleAll()` (боевой ре-арм при перезагрузке телефона) не
   фильтровал по `status`** — переармливал напоминания для завершённых/отменённых/отложенных
   событий на каждой перезагрузке. Фикс: пропускать элементы с `status != ACTIVE`.
4. **Перенос даты события не пересчитывал время напоминаний** — будильник оставался приколот
   к старой дате/времени после «Перенести». Фикс: тот же постпон-хендлер теперь вызывает
   `NotificationScheduler.rescheduleReminders(...)` с новой датой.
5. **Поле «Заметки» в `CompanyEditScreen` не сохранялось НИКОГДА** — `companyNote` был локальным
   `mutableStateOf("")`, не связанным ни с загрузкой существующей заметки компании, ни с записью
   при `Готово`. Классический §отдельный-инпут-без-CRUD: `Note.companyId` как поле в модели давно
   существовало и читалось на экране просмотра компании, но `CompanyEditScreen` никогда не
   писал/не читал через него. Фикс: при открытии — подтягивается последняя `GENERAL`-заметка
   компании по `updatedAt`; при сохранении — `updateNote`/`addNote`/`deleteNote` в зависимости от
   того, пуст ли текст и существовала ли заметка раньше.
6. **Undo слияния (и контактов, и компаний) не убирал авто-заметку «отброшенные поля»**
   (`MergeResolveScreen.kt`, `CompanyMergeResolveScreen.kt`) — заметка о несовпавших полях
   создавалась ПОСЛЕ снапшота, который использует `undoMerge`/`undoMergeCompanies`, поэтому Undo
   не мог её убрать: после отмены слияния оставалась висеть заметка, описывающая слияние, которого
   уже нет. Один и тот же паттерн бага скопирован в оба файла (контакты и компании создавались как
   зеркальные копии, см. §34 «продуктовые решения»). Фикс: id заметки запоминается локально в
   обработчике и удаляется явным `deleteNote` в ветке `ActionPerformed`, отдельно от снапшота.

### Итоговое правило
1. Любой статус/поле enum, который пишется в модель, обязан быть грепнут по всем читающим местам
   ДО того, как считается фичей — «пишем, но никто не читает» и «читаем ACTIVE, а пишем POSTPONED»
   не ловятся компиляцией, только целенаправленным поиском (тот же класс ошибки, что и §50/§85 —
   «своё значение = полный CRUD», только наоборот: тут не забыли дописать читателя новому значению,
   а само значение изначально не имело ни одного читателя).
2. Будильники (`AlarmManager`) — независимая от Room подсистема состояния; ЛЮБАЯ мутация
   календарного события (удаление, завершение, перенос даты, отмена) обязана сопровождаться явным
   вызовом `NotificationScheduler` в том же месте, где есть `Context` — стор сам этого сделать не
   может и не должен молча.
3. Если создаётся синтетическая запись (заметка/лог) КАК ПОБОЧНЫЙ ЭФФЕКТ операции, которая уже
   поддерживает Undo через снапшот — снапшот берётся ДО операции и не увидит запись, созданную
   ПОСЛЕ. Такие побочные записи должны либо входить в сам снапшот, либо отслеживаться отдельным
   id и убираться вручную в обработчике Undo.
4. Копипаст зеркальной архитектуры (контакты↔компании, см. §34) переносит баги так же надёжно, как
   и полезные паттерны — если баг найден в одной из двух «зеркальных» реализаций, вторую нужно
   проверить на тот же паттерн сразу, автоматически, не дожидаясь отдельной жалобы.

### Итоговое правило

   равно «гарантированно цело до конца сессии»; при финальном аудите перепроверять и свежий код, не
   только код прошлых сессий.
2. Если в одном файле настроек часть полей обёрнута в `PersistedMutableState`, а часть — в голый
   `mutableStateOf` — это почти всегда забытая persist-обёртка, а не осознанный выбор; при
   добавлении новой настройки в такой файл сверяться с соседями по паттерну, а не копировать первый
   попавшийся пример.
3. Настройка, которая переключается в UI, но нигде не читается логикой — decorative control, тот
   же класс проблемы, что «кнопка ничего не делает»; разница только в том, что здесь состояние хотя
   бы персистится. Требует явного продуктового решения (подключить или убрать), не мех правки.

## 37. Подключение декоративных настроек напоминаний (§36 п.7) — решение владельца и реализация (2026-07-27)

Владелец выбрал для всех трёх открытых вопросов §36: подключить дефолты напоминаний к созданию
события, подключить `showOverdue`, и для `repeatOverdueVisually` — повторный push с отсрочкой +
подсветка + чтобы уведомление «спрашивало» повторять или нет.

### Находка по пути: снова «кнопка нарисована, но не работает»
При проектировании повтора уведомлений выяснилось, что универсальный механизм «Отложить»/«Готово»
на уведомлениях уже существовал (`NotificationHelper.showNotification` рисует эти кнопки на КАЖДОМ
уведомлении) — но `NotificationReceiver.onReceive` начинался с `val calendarItemId = intent.getStringExtra("calendarItemId") ?: return`.
Для уведомлений без привязки к календарному событию (`targetCalendarItemId = null` — «Пора
связаться», день рождения без события, сводка «без следующего шага» из `StaleContactsReceiver`)
это означало, что весь обработчик выходил в самом начале: кнопки были нарисованы и нажимались, но
ничего не происходило. Это ровно тот класс бага, который вся сессия и искала — просто в этот раз
не аудит-агент его нашёл, а попытка спроектировать новую фичу поверх существующего механизма.

### Реализация
1. **Дефолты напоминаний** (`CalendarItemEditScreen.kt`): для нового события начальный выбор
   в пикере напоминаний берётся из `AppSettings` по `CalendarItemType` (день рождения/годовщина/
   именины/важная дата → `birthdayReminderTimes`, подарок → `giftReminderTime`, встреча/событие
   компании → `meetingReminderTime`, звонок/сообщение → `callReminderTime`, остальное →
   `defaultReminderTime`). Попутно обнаружено и исправлено: пикер напоминаний в форме события
   поддерживал только 6 из 9 значений `ReminderTime` (не было `MIN_30`/`DAY_3`, которые как раз
   предлагают настройки «Встречи»/«Подарки») — расширен до полного набора, иначе подставленный
   дефолт не совпал бы ни с одним чипом (тот же класс бага, что чекбокс адреса компании в §36 п.4).
   `ON_DAY` не добавлен отдельным чипом — для all-day событий (дни рождения) `AT_TIME` и так
   резолвится в 09:00 того же дня (`NotificationScheduler.calculateNotificationTime`), т.е.
   семантически совпадает с `AT_EVENT`.
2. **`showOverdue`** (`HomeScreen.kt`): счётчик «Просроченные» и вся секция «Нужно связаться»
   обёрнуты в `if (AppSettings.showOverdue.value)`.
3. **`repeatOverdueVisually`**: НЕ потребовалась новая схема БД/миграция — только починка описанного
   выше мёртвого обработчика (`calendarItemId` стал nullable по всей цепочке
   `NotificationReceiver`→`NotificationHelper`→`NotificationScheduler.scheduleSnooze`; заодно
   протянут `channel`, которого раньше не было в `actionIntent`/`scheduleSnooze` — без него
   отложенное уведомление переоткрывалось бы в дефолтном канале вместо своего). Это и есть
   «повторный push с отсрочкой» и «спрашивает повторять или нет» — уже существовавший, но
   нерабочий механизм. Настройка `repeatOverdueVisually` сама теперь управляет только визуальной
   частью: жирный красный бейдж «N дн. просрочки» в списке «Нужно связаться» (новая строка
   `home_overdue_days_badge` в 3 локалях).

### Итоговое правило
Прежде чем проектировать новую фичу «с нуля» (особенно если она напоминает уже существующий
механизм — push-уведомления, кнопки действий, snooze) — сначала грепнуть, не существует ли уже
нужной инфраструктуры в сломанном виде. В этом случае вся «новая фича» оказалась однострочным
фиксом (`?:  return` → nullable) в уже написанном коде, а не миграцией БД + новым UI, как
предполагалось на этапе планирования.

## 38. «Тип отношений на греческом» — разобран баг-репорт владельца, живая проверка (2026-07-27)

Владелец сообщил: добавил свой тип отношений на греческом, при смене языка он не перевёлся, и
после создания контакта тип не отображается «в ленте». Разобрано живой проверкой на эмуляторе
(создан тестовый контакт со своим типом, проверены Contacts-список, фильтр, карточка контакта,
Home-экран, смена языка на все 3 локали).

**«Не переводится» — НЕ баг, а архитектура.** Свой тип отношений — обычный текст, который вводит
владелец (`customRelationshipType: String?`), а не выбор из переводимого enum `RelationshipType`.
У произвольного текста просто нет словаря переводов ни на один язык — он хранится и показывается
ровно как был введён, в любой локали приложения. Подтверждено живьём: создал тип на латинице,
переключил язык на Ελληνικά — весь остальной UI перевёлся, текст типа остался как есть, что и
должно происходить. Если нужен другой UX (например, авто-перевод через внешний сервис) — это
отдельная фича, не текущий баг.

**«Не отображается в ленте» — подтверждённый баг, найден и исправлен.** Все места, кроме одного,
показывают `customRelationshipType` корректно (Contacts-список, фильтр «Мои типы связи», карточка
контакта). Единственное реальное место провала — карточка **«Недавно добавленные»** на главном
экране (`HomeScreen.kt`, `HomeRecentCard`): она показывала ТОЛЬКО company/position, тип отношений
там не читался вообще. Для только что созданного контакта без компании (типичный случай сразу
после заполнения формы) карточка не показывала под именем НИЧЕГО — ни компанию, ни тип, хотя тип
был явно задан. Именно это владелец и увидел, назвав экран «лентой». Исправлено: `HomeContact`
получил `relationshipLabel` (тот же паттерн `customRelationshipType?.takeIf{isNotBlank} ?:
relationshipType.label(ctxLabel)`, что и везде), `HomeRecentCard` использует его как третий
fallback после company/position.

### Итоговое правило
1. Жалоба «не отображается» может относиться к ЛЮБОМУ из нескольких мест показа одного и того же
   поля — при разборе перепроверять ВСЕ известные места рендера (список, фильтр, карточка, главный
   экран), не останавливаться на первом же, где всё работает.
2. Разные UI-поверхности одного приложения нередко реализуют один и тот же fallback независимо
   (`customX?.takeIf{isNotBlank} ?: builtin.label(ctx)`) — при добавлении нового поля с таким
   паттерном грепать ВСЕ уже существующие копии этого паттерна и добавлять новую поверхность
   туда же, иначе одна из карточек молча выпадает (как здесь — Home-«Недавно добавленные»
   единственная не скопировала fallback).
3. Разграничивать «баг» и «архитектурное ограничение, о котором стоит явно сказать» — «своё
   значение не переводится» это не баг чат-функции, а прямое следствие того, что это свободный
   текст; объяснять это словами владельцу, а не пытаться «почимнить» несуществующую проблему.

## 40. Три бага целостности данных — календарные ссылки, дедуп компаний, обрезка ФИО (2026-08-02)

Владелец: события календаря теряют привязку к контакту после обновления; профессии/компании
дублируются вместо объединения даже при одинаковом тексте; контакты с 3–4 словами в имени
показывают/ищутся только по 2. Расследовано воркфлоу (root-cause найден по всем трём, фикс + тесты).

1. **Потеря ссылки календарь↔контакт.** `AppStateStore.reloadFromDb()` (только холодный старт)

   когда-либо была сохранена с пустым/неверным `calendarItemId`, она молча исчезает при следующем
   холодном старте, при этом в текущей живой сессии всё выглядит нормально (баг маскируется активным
   тестированием). Фикс — в UI-экране (правильная простановка id) + защита на записи в
   `AppStateStore`. Тест: `DaoTest.calendarItemLink_reattachesOnlyWhenStampedWithRealEventId`.
   **Важно, не сообщено владельцу:** уже испорченные строки на РЕАЛЬНОМ устройстве (если баг успел
   сработать до фикса) автоматически не восстанавливаются — нужно явное решение владельца
   (попытаться восстановить вручную vs принять потерю).
2. **Компании не объединяются.** `CompanyEditScreen.kt` в режиме создания не проверял, существует ли

   Тесты: `CompanyDedupeTest.kt` (3 теста).
3. **Обрезка имени до 2 слов.** Общий форматтер отображения `SearchEngine.formatContactName()` и
   один поисковый предикат не учитывали `middleName` — данные всегда сохранялись полностью
   (никогда не было потери данных), терялось только отображение в списке/гриде и часть поиска.
   Плюс vCard FN-фолбэк (без структурированного `N:`) отбрасывал лишние слова вместо разбора на
   имя+середину+фамилию — тест `vcard_fnFallback_fourWords_keepsAllMiddleWords`.

(п.2 подтверждён кодом), но не исключено, что имелась в виду другая функция — уточнить.

## 41. Мёртвый добредизайновский стек тем (Type/Theme/Color.kt) + иконка приложения не в фирменном цвете (2026-08-03)

Владелец, раздражённо, после установки новой версии: «дизайн опять не исправлен... у тебя есть все
коды, все названия, все шрифты... шрифт не тот, цвет не тот, каёмка не та... мы же поменяли весь код,
чтобы всё было в одном месте». Явное указание искать шрифты/цвета/рамки самому, без наводки на экран.

### Находка 1 — второй, полностью мёртвый дизайн-стек
`ui/theme/Type.kt` + `Theme.kt` + `Color.kt` — набор из добредизайновской генерации Android Studio

`MyApplicationTheme` — по семантике Compose `CompositionLocal` внутренний провайдер побеждает для
всего дерева, так что мёртвый стек не рендерился, но полностью противоречил требованию «всё в одном
месте». `Color.kt` — отдельная старая indigo-палитра «SOCIALSPHERE BRAND PALETTE» (Brand600 =

`MyApplicationTheme(...)`-обёртка из `MainActivity.kt` — остался единственный корень темы,
`AppleAppTheme`. Дополнительно найден и убран мёртвый `BrandIndigo = Color(0xFF5B53D6)` в самом
`AppleDesignSystem.kt` (канонический файл, но с забытым добредизайновским остатком внутри).

### Находка 2 — иконка приложения, живой видимый баг
`res/drawable/ic_launcher_background.xml` (`#4F3DC7`) и `ic_launcher_foreground.xml` (буква «S»,

### Дисциплина
Растровые `mipmap-*dpi/ic_launcher*.webp` (API 24–25 фолбэк, кэш лаунчера) — бинарные, регенерируются

## 43. Шифрование БД (SQLCipher) — план готов, реализация НЕ начата, ждёт решения владельца (2026-08-11)

Владелец дважды подчеркнул «очень важная задача» — зашифровать Room БД без потери данных ни при
переходе, ни при будущих апдейтах. Расследовано `socialsphere-plan-feature` (research + codebase-
impact + design-fit → синтез; критик упал по лимиту сессии субагентов, синтез уже был готов).
**Реализация сознательно НЕ начата в этом заходе** — это самая необратимая из всех задач сессии
(реальные пользовательские данные на реальном устройстве), автоматическая адверсариальная проверка
плана не прошла (упала по лимиту), и план содержит явный открытый продуктовый вопрос — начинать
писать код при этих условиях означало бы именно тот риск, от которого владелец просил защититься.

**Ключевые решения плана** (полный текст — в истории задачи воркфлоу, не дублируется тут построчно):
- Библиотека: `net.zetetic:sqlcipher-android` (НЕ deprecated `android-database-sqlcipher`, EOL 2023,
  нет сборки под 16 KB page size — блокер Google Play при targetSdk 36). Интеграция через
  `SupportOpenHelperFactory` в тот же `.openHelperFactory(...)` слот, что Room 2.6.1 уже поддерживает.
- Ключ: envelope-схема — случайные 32 байта прямо в SQLCipher, обёрнуты AES-256-GCM ключом из
  `AndroidKeyStore` (+ StrongBox с фолбэком). **Критично:** `setInvalidatedByBiometricEnrollment(false)`
  обязателен — дефолт/копипаст из туториалов про биометрию убил бы ключ БД при обычной смене
  отпечатка пальца, необратимо. Отдельный Keystore-алиас от PIN/биометрии экрана (`AppLockComponents.kt`).
- Миграция существующих данных: файловая (не Room-миграция схемы — `version=18` не меняется,
  `MIGRATION_1_2…17_18` не трогаются) — WAL checkpoint → `sqlcipher_export()` во временный файл →
  верификация (`PRAGMA integrity_check` + построчный `COUNT(*)` по всем 19 таблицам) ДО касания
  оригинала → rename-swap с `.pre-encryption.bak`, который не удаляется автоматически никогда.
  Любая ошибка на любом шаге — оригинал остаётся нетронутым, флаг `NOT_MIGRATED` не меняется.
- **Находка синтеза (проверено напрямую в коде, важно):** `getDatabase()` вызывается не только из
  `MainActivity.kt`, но и синхронно из `BootReceiver`/`StaleContactsReceiver` (headless, без UI,
  бюджет `goAsync()` ~10 сек) — тяжёлая миграция ТАМ рисковала бы ANR. Решение: `allowMigration`
  параметр, `true` только на вызове из `MainActivity`, оба receiver'а получают безопасный дефолт `false`.
- Тестовая инфраструктура: юнит-тесты (`DaoTest`/`MigrationTest`, Robolectric/JVM) НЕ переводить на
  `SupportOpenHelperFactory` — нативная `libsqlcipher.so` не грузится под JVM
  (`UnsatisfiedLinkError`), это сломает весь текущий unit-suite. Нужны 5 НОВЫХ инструментальных
  (`androidTest`) тестов — единственный существующий файл там сейчас пустая заглушка.

**Открытый вопрос владельцу (план прямо отказывается решать самостоятельно):** recovery-механизм при
недоступности Keystore-ключа. Вариант A (рекомендация плана, минимум нового кода) — переиспользовать
уже существующий и протестированный `ExportManager.exportFullZip()` с обязательной одноразовой
подсказкой сохранить бэкап перед включением шифрования. Вариант B — отдельный recovery-код (24
символа, второй wrapped-blob) — больше нового крипто-кода и новый UI-экран. Нужен ответ владельца до
написания `DbKeyManager.kt`.

**Как продолжить:** после ответа на открытый вопрос — реализовать по плану (точный список файлов
есть в тексте задачи), обязательно с полным набором из 10 живых проверок и 5 инструментальных
тестов, описанных в плане, прежде чем считать задачу закрытой.

## 44. Частичный бэкап (заметки/календарь отдельно) + найдена и починена реальная дыра в существующем бэкапе (2026-08-11)

Владелец, вместо полного шифрования БД (пока ждёт решения по recovery, см. §43), предложил
альтернативу попроще: раз «заметки и календарь постоянно страдают», дать возможность сохранять и
восстанавливать их ПООТДЕЛЬНОСТИ, не трогая всю базу. Заодно попросил проверить, не страдает ли
что-то ещё так же.

**Найдено при проверке — существующий полный JSON-бэкап (`ExportManager.exportJsonBackup`/
`importJsonBackup`) имел ДВЕ реальные, ранее не замеченные дыры:**
1. **Заметки компаний (`Note.companyId`, без `contactId`) вообще не попадали в бэкап.** `BackupData`
   не имела top-level поля `notes` — заметки читались только как вложенное `Contact.notes`
   (корректно синхронизируется `addNote`/`updateNote`/`deleteNote`). Но у `Company` нет поля `notes`
   вообще (модель это подтверждает) — значит заметки, привязанные к компании (в т.ч. после
   `convertContactToCompany()`/переноса при слиянии компаний), не сериализовались НИКУДА. Если бы
   владелец когда-нибудь воспользовался восстановлением из бэкапа — все заметки компаний исчезли бы
   безвозвратно, и бэкап их не спас бы.
2. **Восстановленные заметки контактов не переживали следующий холодный старт.** `importJsonBackup`
   вызывает `restoreContact(c)` для каждого контакта из бэкапа (с уже вложенными `c.notes`), но
   `restoreContact` → `addContactDb` НИКОГДА не пишет в таблицу `notes` (только phones/emails/
   messengers/companyRelations/addresses/personalDetails/sizeInfo). Заметки появлялись в
   `AppStateStore.contacts[i].notes` только в оперативной памяти — на следующем `reloadFromDb()`
   (перезапуск приложения) они полностью пропадали, т.к. в БД их не было. Это прямое, воспроизводимое
   объяснение классa жалоб «восстановил бэкап — заметки опять пропали после перезапуска».

**Фикс (закрывает обе дыры разом, не только для partial-фичи):**
- `BackupData` получила top-level `notes: List<Note>` (версия бэкапа 4→5, default `emptyList()` —
  старые бэкапы по-прежнему парсятся), источник — `AppStateStore.notes` (плоский список, единственный
  источник истины, покрывает и контактные, и компанийные заметки).
- Новая `AppStateStore.restoreNote(note)` — upsert по id БЕЗ перезаписи `createdAt/updatedAt` (тот же
  идиом, что `restoreContact`/`restoreGroup`/`restoreTag`), синхронизирует вложенный `Contact.notes`
  при наличии `contactId`, и — критично — реально пишет в `noteDao().insertNotes(...)`.
- Новая `AppStateStore.restoreCalendarItem(item)` — аналогично, для консистентности: `importJsonBackup`
  раньше вызывал `updateCalendarItem`/`addCalendarItem`, которые штампуют новый `createdAt/updatedAt`,
  затирая исходные даты бэкапа (тот же класс правки, что уже применён к контактам). Теперь и полный, и
  частичный restore календаря используют `restoreCalendarItem`.
- `importJsonBackup` теперь явно восстанавливает `data.notes` — полный бэкап отныне действительно
  полный.

**Новая фича (собственно то, что попросил владелец):** `exportNotesJson`/`importNotesJson` и
`exportCalendarJson`/`importCalendarJson` в `ExportManager.kt` — тот же формат `BackupData`, но
заполнено только одно поле; импорт-функции трогают СТРОГО свою категорию, даже если в файле случайно
окажутся другие данные (защита от использования не того файла). UI — новая секция «Частичный бэкап» в
`ImportExportSettingsScreen.kt`, 4 строки (сохранить/восстановить заметки, сохранить/восстановить
календарь), паттерн 1-в-1 с уже существующими для полного JSON. Строки локализованы в 3 языках.

**Тесты:** `ExportManagerTest.kt` — round-trip для заметки компании (прямая регрессия на находку #1),
round-trip для файлов «только заметки»/«только календарь» (частичный формат), обновлён
`roundTrip_fullBackup_preservesEveryField` с новым полем `notes`. Все — на уровне чистой сериализации
`BackupData` (JVM, без Robolectric/Room), тем же паттерном, что и весь остальной файл.

**Урок:** запрос «сделай попроще, по частям» из уст владельца — не понижение сложности, а часто способ
найти реальный баг: чтобы построить partial-export, пришлось пройти путь `Note` от UI до БД целиком и
обнаружить, что «полный» бэкап был неполным. Всегда стоит трассировать весь путь данных для новой
фичи, а не только добавлять новый код поверх старого пути вслепую.

## 45. Фантомные «контакты» при импорте из телефона — баг был починен только в 2 из 3 путей импорта (2026-08-11)

Владелец: «постоянно добавляются какие-то контакты типа, какие-то вместо контактов, какие-то то ли
группы, то ли компании, непонятно что... мы это уже решали, и всё равно появляется». Плюс отдельная
жалоба: добавил контакт в телефон — сложно добавить именно его одного в приложение, не дублируя всё
заново; в списке импорта нет ни поиска, ни фильтров.

**Root cause найден.** В `ContactImporter.kt` есть ТРИ независимых парсера — `parseVCard()`,
`parseCsv()`, `getDeviceContacts()`. Первые два УЖЕ имеют явный фильтр «запись должна иметь хотя бы
телефон или email» с комментарием прямо об этом («Группы/метки телефонной книги приходят как карточки
с именем, но без телефона и email — отсекаем их») и регресс-тестами
(`vcard_cardWithoutPhoneOrEmail_isDropped`, `csv_rowWithoutNameOrPhone_isSkipped`). А вот
`getDeviceContacts()` (путь «Импорт из телефонной книги» — наиболее используемый из трёх, ЭТО и есть
тот самый «мы это уже решали») отдавал `candidates.values.toList()` БЕЗ единого фильтра — абсолютно
всё, что попадалось в курсоре `ContactsContract.Data`, включая ярлыки групп синхронизации,
записи от сервис-аккаунтов (WhatsApp и т.п.) и прочие непользовательские строки без телефона/email.
Баг был исправлен только в 2 из 3 мест — третье, главное, никогда не было тронуто тем прошлым фиксом.

**Фикс:** `.filter { it.phones.isNotEmpty() || it.emails.isNotEmpty() }` на выходе
`getDeviceContacts()` — тот же ровно предикат, что уже стоит в двух других парсерах.

**Вторая жалоба (поиск одного нового контакта в списке импорта):** `ImportPreviewScreen` показывал
плоский `LazyColumn` без единого поиска/фильтра — при большом телефонном списке найти ОДИН только что
добавленный контакт вручную скроллом было нереально, а по умолчанию ВСЕ новые кандидаты уже
предвыбраны (`selectedForImport = true`), так что для импорта «только этого одного» пришлось бы
руками снять галочки со всех остальных. Добавлены: поисковое поле (фильтрует ТОЛЬКО отображение,
чекбоксы вне видимой области не трогает) + «Выбрать все»/«Снять все», действующие только на видимые
(отфильтрованные) карточки — можно сузить поиск до одного имени и одним тапом выбрать/снять именно
его, не трогая остальные сотни контактов.

**Не сделано в этом заходе:** отдельный Robolectric-тест на `getDeviceContacts()` — функция читает
`ContentResolver`/`Cursor` напрямую, требует полноценного мока `ContactsContract`, что заметно
тяжелее, чем однострочный фикс это оправдывает; логика идентична уже протестированным
`parseVCard`/`parseCsv`, риск невысокий. Живая проверка на эмуляторе с реальными синхронизированными
аккаунтами (Google/WhatsApp) — тоже не пройдена, только code-review + компиляция.
